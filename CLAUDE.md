# AgentDeck

macOS daemon that works through a queue of coding tasks with `claude -p`, one git worktree per task, paced to the user's Claude quota. `daemon/` is Node + TypeScript on `node:sqlite`; `app/` is the Tauri 2 + Vue 3 dashboard.

## Commands

`pnpm test` · `pnpm typecheck` · `pnpm format` · `pnpm check:fast` (`format:check`, `typecheck`, `db:check`, `test`) · `pnpm check` (`check:fast`, then the SIGKILL crash test, `CRASH_ITERATIONS` runs, default 10) · `pnpm docs:gen` (generate the architecture docs) · `pnpm rules` (print each rule with its checks) · `pnpm check:rust` (fmt, clippy and tests of `app/src-tauri`; not part of `pnpm check`, CI runs it via `.github/workflows/rust.yml` whenever `app/src-tauri` changes) · `node daemon/scripts/crash-test.mjs 10` (the crash test alone)

@GLOSSARY.md

Use the words in the glossary in code, logs and UI. Plans are named `<task id>-<slug>.html` (`docs/plan-format.md`); attach one with `agentdeck add --plan <file>` (any path) or `agentdeck attach`, and other tasks follow it with `--plan <task number>`.

## Boundaries

`daemon/src/` is layered. Imports point down the list: an outer layer may import an inner one, never the reverse. <!-- rule:layers -->

- **`domain/` is pure:** no I/O and no imports from other layers. It holds the entities (`Repo`, `Task`, `Run`, `PlannerRun`) and the decisions: task lifecycle, governor, prompts, tool rules, toolchain detection, planner proposals, plan parsing and PR bodies. One folder per aggregate: `task/`, `repo/`, `run/`, `planner/` (`proposals.ts`), `plan/`, `review/` (a task's reviews and line comments, and how a comment's state moves), `usage/`, `pull-request/`, `settings/`, `branch/` (`sync.ts`: how a sync is worded), `daemon/` (the daemon's health and headline), `files/` (a task's changed files), plus `notification.ts` (notification kinds) and `time.ts` beside them. A task's `Needs` are in `task/needs.ts` and its prompt sections (`PROMPT_SECTIONS`) in `task/task.ts`; shared text helpers such as `lastLine` are in `text.ts`. <!-- rule:domain-pure -->
- **Queries live only in `db/`, through Drizzle** (raw `sql` only where the builder hides a guard), one store per table group merged into one `Db` in `db/index.ts`. The tables are in `db/tables.ts`, the migrations in `db/schema.ts`. Every task status change is a guarded `UPDATE … WHERE status IN (…)` (`applyEvent` in `db/tasks.ts`, and `claimNextTask` beside it for the claim), never a raw status write. <!-- rule:sql-in-db --> <!-- rule:guarded-status -->
- **`adapters/` hold the I/O** (claude, processes, git, github, shell, notify, service, run logs, goals files). They import `domain/` and `config.ts` only, never `db/` or `application/`: they report through callbacks like `runClaude`'s `onUsage`. <!-- rule:adapters-io -->
- **`application/` holds the use cases,** connecting domain, db and adapters, in folders that mirror `domain/`'s aggregates: `scheduler/scheduler.ts`, `run/worker.ts`, `planner.ts`, `pull-request/merge.ts` and `pull-request/refresh.ts` (merging a PR, and keeping open PRs' state fresh), `sync.ts` (syncing task branches with the base branch), `plans.ts`, `repo/doctor.ts`, `daemon/doctor.ts` (`agentdeck doctor`: the daemon's health, judged in `domain/daemon/health.ts`), and the person-facing use cases in `repo/repos.ts`, `task/tasks.ts`, `review/reviews.ts` and `settings.ts`. `actions.ts` re-exports those for the CLI and the API; it is the only application module they import. Request parsing and `ActionError` are in `input.ts`. <!-- rule:actions-only -->
- **Entry points:** `api/` (the dashboard's HTTP API) and `cli/` (one file per command group). They may import `domain/` and `db/`, but reach adapters only through `application/`. `src/cli.ts` stays put: the installed launchd plist runs it. <!-- rule:entry-points -->
- **The CLI calls the use cases in its own process,** so it works while the daemon is down. Only work that starts `claude` (propose, a sync that may start a resolve run) goes to the daemon over HTTP (`cli/daemon-client.ts`). So the database is the only state the processes share: application code keeps no module-level state other than a lock or a cache of immutable results, and a CLI change reaches the scheduler on its next tick. Each entry point parses its own input (flags, request bodies) into the use case's typed input. <!-- rule:cli-in-process --> <!-- rule:no-module-state -->
- **Composition root:** `src/daemon.ts` (`runDaemon`) wires the source watcher, the API and the scheduler. It logs through a callback and throws; `cli/daemon.ts` prints and exits. <!-- rule:composition-root -->
- **Dashboard types:** the API's request and response types are in `api/contract.ts`, which imports only types, and only from `domain/`. The dashboard imports them (`app/src/api/types.ts`). Each route names the type it answers with (`route<T>` in `api/http.ts`), and `api/contract-check.ts` checks the request types against the use cases, so `pnpm typecheck` fails when a use case's type drifts from them. <!-- rule:contract-types -->
- **Dashboard layout (`app/src/`):** `api/` (types, calls and wording, imported as `api`), `composables/` (`useX` functions), `lib/` (pure helpers; rules come from the daemon's `domain/`, never copied), `platform/` (the Tauri shell, build commit, theme), `styles/`, and `components/` by area: `ui/` (shared pieces), `layout/` (the app's frame), `panels/`, `queue/`, `task/`, `files/`, `insights/` (the scorecard over time). <!-- rule:dashboard-layout -->

## Rules

`daemon/test/architecture.test.ts` checks the Boundaries above, plus the dependency, migration and process-group rules below. Each failure names the file, line and rule. The map of the code is `docs/architecture.md`. A new rule gets a check, or goes on the unchecked list with its reason (`daemon/scripts/lib/rules.ts`); `pnpm rules` prints each rule with its checks.

- **No folder cycles.** Folders in `domain/` and in `application/` import each other without cycles, counting runtime and type imports. The cycles there today are on `ALLOWED_FOLDER_CYCLES` (`daemon/scripts/lib/progress.ts`), a list that only shrinks: a new cycle fails, and so does an entry that no longer applies. `docs/reference/progress.md` counts what is left. <!-- rule:folder-cycles -->
- **Erasable TypeScript only.** Node runs `.ts` directly, so no enums, namespaces or constructor parameter properties. <!-- rule:erasable-ts -->
- **No new runtime dependencies** without a reason. The one there is, `drizzle-orm`, is pinned at exactly `1.0.0-rc.5` (no caret) (`docs/plans/drizzle.html`); use only its core query builder, not the relational query API. `pnpm db:studio` browses the live database. <!-- rule:no-runtime-deps -->
- **Schema changes are appended as new migration steps.** Never edit a step that has shipped. To add a column: (1) add it to its table in `db/tables.ts` and to the domain type; (2) run `pnpm db:generate`, which prints the SQL that makes a migrated database match `tables.ts`; (3) append that SQL as a new step in `db/schema.ts`; (4) run `pnpm db:check` and `pnpm typecheck` (`db/types-check.ts`), which fail until `tables.ts`, the migrations and the domain type agree; (5) use the column in the store's queries; (6) once the step is final, append the hash the test prints to `daemon/test/migrations.lock`. <!-- rule:migrations-append -->
- **Use the glossary's words.** An `_Avoid_:` word in `GLOSSARY.md` appears nowhere in `daemon/src` or `app/src`. "Hold" (hold, holds, held, holding) is the governor's word alone (`domain/usage/`, the scheduler's announcement, the `hold` notification kind); a repo or the daemon is paused, and anywhere else say wait or keep. Other uses are on the check's allow-list, each with its reason. <!-- rule:vocabulary -->
- **A state machine is a rule table in `domain/`** (`RULES` in `task/lifecycle.ts`, `COMMENT_MOVES` in `review/review.ts`), and `pnpm docs:gen` lists it in `docs/reference/state-machines.md`. A state type no table drives is on the allow-list in `daemon/scripts/lib/model-docs.ts` with its reason; pull request state and merge requests are there until they are tables. <!-- rule:state-as-data -->
- **Every `claude` runs in its own process group** with its pid recorded on the run, so crash recovery can stop it. <!-- rule:claude-process-group -->
- **Keep this checkout on `main`.** The installed daemon runs its `daemon/src/cli.ts`, so switching branches here swaps the live daemon's code. Try task branches from their worktrees. <!-- rule:main-checkout -->
- **Delegating to AgentDeck:** when to queue a task instead of doing it here, how to write it, and how to work in a task's worktree are in the `delegate` skill (`.claude/skills/delegate/SKILL.md`). <!-- rule:delegate-skill -->
