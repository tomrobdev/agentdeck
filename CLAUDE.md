# AgentDeck

macOS daemon that works through a queue of coding tasks with `claude -p`, one git worktree per task, paced to the user's Claude quota. `daemon/` is Node + TypeScript on `node:sqlite`; `app/` is the Tauri 2 + Vue 3 dashboard.

## Commands

`pnpm test` · `pnpm typecheck` · `pnpm format` · `pnpm check:fast` (`format:check`, `typecheck`, `db:check`, `coverage`) · `pnpm check` (`check:fast`, then the SIGKILL crash test, `CRASH_ITERATIONS` runs, default 10) · `pnpm check:task` (the one check a task's branch must pass, and the AgentDeck repo's `test_cmd`: `check:fast`, then the crash test, 5 runs, when the branch changes `daemon/src/application/runs/`, `daemon/src/application/scheduler/`, `daemon/src/adapters/processes.ts`, `daemon/src/adapters/claude.ts` or `daemon/src/db/` against `origin/main`, and `check:rust` when it changes `app/src-tauri/`; it prints which it ran and why, and the rules are in `daemon/scripts/lib/check-task.ts`) · `pnpm coverage` (the tests with coverage, against the floors; check:fast runs it in place of `pnpm test`) · `pnpm docs:gen` (generate the architecture docs) · `pnpm rules` (print each rule with its checks) · `pnpm check:rust` (fmt, clippy and tests of `app/src-tauri`; not part of `pnpm check`, CI runs it via `.github/workflows/rust.yml` whenever `app/src-tauri` changes) · `node daemon/scripts/crash-test.mjs 10` (the crash test alone)

@GLOSSARY.md

Use the words in the glossary in code, logs and UI. Plans are named `<task id>-<slug>.html` (`docs/plan-format.md`); attach one with `agentdeck add --plan <file>` (any path) or `agentdeck attach`, and other tasks follow it with `--plan <task number>`.

## Boundaries

`daemon/src/` is layered. Imports point down the list: an outer layer may import an inner one, never the reverse. <!-- rule:layers -->

- **`domain/` is pure:** no I/O and no imports from other layers. It holds the entities (`Repo`, `Task`, `Run`, `PlannerRun`) and the decisions: task lifecycle, governor, prompts, tool rules, toolchain detection, planner proposals, plan parsing and PR bodies. One folder per bounded context (see Contexts in `GLOSSARY.md`): `work/` (tasks, links, stages, branch names, `plan.ts`; `work/read/` for listings, the digest and a task's changed files), `runs/` (runs, prompts, unblock runs, `resolve.ts`: how a resolve run's end settles its sync; `runs/translate/` for the run log, live state and sandbox settings), `landing/` (pull requests, checks, merging, `sync.ts`: how a sync is worded, and reviews with their line comments and how a comment's state moves), `repos/` (repos with their PR mode and merge method, tool rules, toolchain detection, protected edits), `capacity/` (the usage windows and the governor), `proposals/` (the planner's proposals), `operations/` (the daemon's health, headline and restart, notification kinds, settings), `insights/` (the scorecard and what is counted over time) and `shared/` (`text.ts`, `time.ts`, `id.ts`). The contexts import each other one way: proposals, runs → work → landing → repos, with capacity below and insights and operations above, reading the others. A task's `Needs` are in `work/needs.ts` and its prompt sections (`PROMPT_SECTIONS`) in `work/task.ts`; shared text helpers such as `lastLine` are in `shared/text.ts`. <!-- rule:domain-pure -->
- **Queries live only in `db/`, through Drizzle** (raw `sql` only where the builder hides a guard), one store per table group merged into one `Db` in `db/index.ts`. The tables are in `db/tables.ts`, the migrations in `db/schema.ts`. Every task status change is a guarded `UPDATE … WHERE status IN (…)` (`applyEvent` in `db/tasks.ts`, the claim included), never a raw status write. <!-- rule:sql-in-db --> <!-- rule:guarded-status -->
- **`adapters/` hold the I/O** (claude, processes, git, github, shell, notify, service, run logs, goals files). They import `domain/` and `config.ts` only, never `db/` or `application/`: they report through callbacks like `runClaude`'s `onUsage`. <!-- rule:adapters-io -->
- **`application/` holds the use cases and imports only itself, `domain/` and `config.ts`.** It reaches the database through the repository interfaces it declares in `ports/repositories.ts` (in domain types; `db/` implements them, and an interface lists only what use cases call) and the I/O through the other ports in `ports/` (`Agent`, `CodeHost`, `Workspace`, `Source` and the rest), whose real adapters `compose.ts` builds. Only `compose.ts` names `db/` and `adapters/`. Every use case takes `app: App` (`ports/app.ts`: the repositories and the ports, one object). It is in one folder per context, as in `domain/`, with `scheduler/scheduler.ts` and `actions.ts` above them and `shared/input.ts` below them: `runs/worker.ts`, `runs/sync.ts` (syncing task branches with the base branch, and its resolve run), `proposals/planner.ts`, `landing/merge.ts` and `landing/refresh.ts` (merging a PR, and keeping open PRs' state fresh), `landing/settle.ts` (every status change and its follow-ups, `FOLLOW_UPS` in `domain/work/follow-ups.ts`; the only caller of `applyEvent`), `work/plans.ts`, `work/checkout-locks.ts` (the sync and merge locks), `repos/doctor.ts`, `operations/doctor.ts` (`agentdeck doctor`: the daemon's health, judged in `domain/operations/health.ts`), and the person-facing use cases in `repos/repos.ts`, `work/tasks.ts`, `landing/person-events.ts` (a person's lifecycle events, through `settle.ts`), `landing/reviews.ts` and `operations/settings.ts`. The contexts import each other one way: proposals → runs → landing, repos → work → operations → capacity, and insights only `shared/`. `actions.ts` re-exports those for the CLI and the API; it is the only application module they import. Request parsing and `ActionError` are in `shared/input.ts`. <!-- rule:ports --> <!-- rule:actions-only -->
- **Entry points:** `api/` (the dashboard's HTTP API) and `cli/` (one file per command group). They import `application/actions.ts`, `domain/` and the contract, never `db/` or `adapters/`: every store call is a use case. `src/cli.ts` stays put: the installed launchd plist runs it. <!-- rule:entry-points -->
- **The CLI calls the use cases in its own process,** so it works while the daemon is down. Only work that starts `claude` (propose, a sync that may start a resolve run) goes to the daemon over HTTP (`cli/daemon-client.ts`). So the database is the only state the processes share: application code keeps no module-level state other than a lock or a cache of immutable results, and a CLI change reaches the scheduler on its next tick. Each entry point parses its own input (flags, request bodies) into the use case's typed input. <!-- rule:cli-in-process --> <!-- rule:no-module-state -->
- **Composition root:** `src/compose.ts` builds the `App` on the database and the real adapters, for the CLI and the daemon (tests build theirs with `testApp` in `daemon/test/fixtures.ts`). `src/daemon.ts` (`runDaemon`) wires the source watcher (the `Source` port), the API and the scheduler on the App it is given. It logs through a callback and throws; `cli/daemon.ts` prints and exits. <!-- rule:composition-root -->
- **Dashboard types:** the API's request and response types are in `api/contract.ts`, which imports only types, and only from `domain/`. The dashboard imports them (`app/src/api/types.ts`). Each route names the type it answers with (`route<T>` in `api/http.ts`), and `api/contract-check.ts` checks the request types against the use cases, so `pnpm typecheck` fails when a use case's type drifts from them. <!-- rule:contract-types -->
- **Dashboard layout (`app/src/`):** `api/` (types, calls and wording, imported as `api`), `composables/` (`useX` functions), `lib/` (pure helpers; rules come from the daemon's `domain/`, never copied), `platform/` (the Tauri shell, build commit, theme), `styles/`, and `components/` by area: `ui/` (shared pieces), `layout/` (the app's frame), `panels/`, `queue/`, `task/`, `files/`, `insights/` (the scorecard over time). <!-- rule:dashboard-layout -->

## Rules

`daemon/test/architecture.test.ts` checks the Boundaries above, plus the dependency, migration and process-group rules below. Each failure names the file, line and rule. The map of the code is `docs/architecture.md`. A new rule gets a check, or goes on the unchecked list with its reason (`daemon/scripts/lib/rules.ts`); `pnpm rules` prints each rule with its checks.

- **No folder cycles.** Folders in `domain/` and in `application/` import each other without cycles, counting runtime and type imports. The cycles there today are on `ALLOWED_FOLDER_CYCLES` (`daemon/scripts/lib/progress.ts`), a list that only shrinks: a new cycle fails, and so does an entry that no longer applies. `docs/reference/progress.md` counts what is left. <!-- rule:folder-cycles -->
- **Contexts are imported through their `index.ts`.** Each folder under `domain/` has an `index.ts` of named exports, no `export *`. Another context, the layers above and the dashboard import a context only through it, so nothing outside a context reaches into its files or into `read/` or `translate/`. An export nothing outside the context imports is removed. <!-- rule:contexts -->
- **Erasable TypeScript only.** Node runs `.ts` directly, so no enums, namespaces or constructor parameter properties. <!-- rule:erasable-ts -->
- **No new runtime dependencies** without a reason. The one there is, `drizzle-orm`, is pinned at exactly `1.0.0-rc.5` (no caret) (`docs/plans/drizzle.html`); use only its core query builder, not the relational query API. `pnpm db:studio` browses the live database. <!-- rule:no-runtime-deps -->
- **Schema changes are appended as new migration steps.** Never edit a step that has shipped. To add a column: (1) add it to its table in `db/tables.ts` and to the domain type; (2) run `pnpm db:generate`, which prints the SQL that makes a migrated database match `tables.ts`; (3) append that SQL as a new step in `db/schema.ts`; (4) run `pnpm db:check` and `pnpm typecheck` (`db/types-check.ts`), which fail until `tables.ts`, the migrations and the domain type agree; (5) use the column in the store's queries; (6) once the step is final, append the hash the test prints to `daemon/test/migrations.lock`. A new step only adds, never renames or drops: the CLI migrates as soon as it runs on pulled code, while a daemon on older code may still be running. <!-- rule:migrations-append -->
- **Models, not rows.** A store reads a whole row of `tasks`, `repos` or `runs` only through `db/mappers.ts` (`toTask`, `toRepo`, `toRun`), so a domain type need not equal its row: `db/types-check.ts` fails when a mapper leaves a column unaccounted for. The flags and JSON documents left on domain entities are on `ROW_SHAPED_FIELDS` (`daemon/scripts/lib/progress.ts`), a list that only shrinks: a new one fails, and so does an entry that no longer applies. <!-- rule:models-not-rows -->
- **A task write with a rule is a domain function.** A write to `tasks` other than a status change (PR state and checks, merge requests, auto-merge, a question) takes its changes from a pure function in `domain/work/task-writes.ts`; the store in `db/tasks.ts` only persists them under its guard. A plain write (the checkout, an edit, a lock) stays in the store and is on `PLAIN_TASK_WRITES` (`daemon/scripts/lib/progress.ts`) with its reason, a list that `docs/reference/progress.md` counts: a new `.update(tasks)` that is neither fails. <!-- rule:task-writes -->
- **Ids are branded.** `TaskId`, `RepoId`, `RunId`, `ReviewId` and `PlannerRunId` (`domain/shared/id.ts`) are numbers the compiler keeps apart, erased at runtime. An entry point parses an id once (`parseId`, `parseTaskIds`); stores return branded ids (the table columns say so in `db/tables.ts`), and use cases take them. A domain or contract field named `…_id` or `…Id` is never typed `number`. A test makes an id with `asTaskId` and the like. <!-- rule:branded-ids -->
- **Use the glossary's words.** An `_Avoid_:` word in `GLOSSARY.md` appears nowhere in `daemon/src` or `app/src`. "Hold" (hold, holds, held, holding) is the governor's word alone (`domain/capacity/`, the scheduler's announcement, the `hold` notification kind); a repo or the daemon is paused, and anywhere else say wait or keep. Other uses are on the check's allow-list, each with its reason. <!-- rule:vocabulary -->
- **A state machine is a rule table in `domain/`** (`RULES` in `work/lifecycle.ts`, `COMMENT_MOVES` in `landing/review.ts`), and `pnpm docs:gen` lists it in `docs/reference/state-machines.md`. A state type no table drives is on the allow-list in `daemon/scripts/lib/model-docs.ts` with its reason; pull request state and merge requests are there until they are tables. <!-- rule:state-as-data -->
- **Coverage floors only rise.** `pnpm coverage` runs the daemon tests with coverage and prints line and branch coverage per group: `domain/<context>`, `db`, `adapters`, `application/<context>`, `api`, `cli`. It fails when a group drops below its floor on `COVERAGE_FLOORS` (`daemon/scripts/lib/progress.ts`), and says to raise a floor beaten by more than 2 points; never lower one. A new group gets a floor at its numbers rounded down. `docs/reference/coverage.md` lists the floors; CI runs `pnpm coverage`. <!-- rule:coverage-floors -->
- **Every `claude` runs in its own process group** with its pid recorded on the run, so crash recovery can stop it. <!-- rule:claude-process-group -->
- **Keep this checkout on `main`.** The installed daemon runs its `daemon/src/cli.ts`, so switching branches here swaps the live daemon's code. Try task branches from their worktrees. <!-- rule:main-checkout -->
- **Every source file is in a review area.** `docs/review-areas.md` maps `daemon/src/` and `app/src/` into the areas the `review-area` skill reviews; a new file goes under its area, and a moved one is moved there too. <!-- rule:review-areas -->
- **CI runs nothing a task's check skips.** Every `run:` step in `.github/workflows/` is a part of `check:fast` or an extra check of `pnpm check:task` (`daemon/scripts/lib/check-task.ts`), or setup listed with its reason, and each check step is named. A new CI check goes into `check:task` too, so a worker whose tests passed isn't failed by one it never ran. <!-- rule:ci-parity -->
- **Delegating to AgentDeck:** when to queue a task instead of doing it here, how to write it, and how to work in a task's worktree are in the `delegate` skill (`.claude/skills/delegate/SKILL.md`). <!-- rule:delegate-skill -->
