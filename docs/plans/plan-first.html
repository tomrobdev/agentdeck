Plan first, then build

Let a person check how a task will be done before it spends a full run building. A plan-first task runs once to write its plan and stops; it waits for approval with the plan on its page; approval queues the build, which follows the plan and ticks off its steps while the card shows the progress live. Written 2026-10-19, after docs/plans/plan-files.html.

Why

The pilot's costly failures come from a wrong approach, not from bad code: a run goes the wrong way for 40 turns, and the review happens after the quota is spent. A plan costs a few turns and can be read in a minute. Plan files now exist, attach themselves to tasks and show on Overview, so the gate is mostly lifecycle and prompt work.

Decisions

Decision Why
A plan ready for review is a proposed task, not a new status Proposed already means "needs you": the queue groups it, Approve and Reject exist, and notifications fire. A new status would touch the lifecycle, ls groups, board columns and every label. The page tells the two apart by the task's plan_first flag.
The planning run doesn't use an attempt max_attempts is for builds. Giving the attempt back works like rate_limited does today.
Live progress reads the worktree's files, not commits Agents commit at the end. The collect at the end of the run stays the one that counts.
The planning run may write only under docs/plans/ A plan run that edits code would be a build nobody approved. Enforced with tool rules, not just the prompt.

1 · Live progress

While a task runs, the worker reads the plans under the worktree's docs/plans/ every 15 seconds and saves those that changed. A new adapter reads the files; collectPlans takes its file list from either source.

2 · Progress in the queue

Task summaries carry plan: { finished, total } | null, shown as a small bar on list rows and board cards. Parsing every plan on every list read is wasteful, so db/plans.ts keeps parsed plans keyed by id and updated_at.

3 · Plan-first tasks

  • Migration step 8: tasks.plan_first. Set with agentdeck add --plan-first and a checkbox in the new task form.
  • The first run gets a planning prompt: write docs/plans/task-<id>.html in the plan format, change nothing else, end with STATUS: DONE.
  • A new lifecycle event planned moves running → proposed through applyEvent, gives the attempt back and notifies. No plan collected means blocked: "the planning run wrote no plan".

4 · Build follows the plan

When a task has a plan, buildPrompt names it and tells the agent to follow it, set each step's data-status as it goes, and commit the plan with the work. A step it can't do is marked blocked with the reason in the step.

Done in docs/plans/plan-linked-tasks.html, step prompt.

5 · Request changes

On a planned proposal, Request changes takes a note and queues another planning run with the note in its prompt. The note is kept as the event's reason, so the timeline shows it. Reject still cancels.

6 · Pilot

Run a plan-first wave on the demo repo and on AgentDeck. Add to the scorecard: plans approved without changes, and plan-first builds done on their first run against the same measure for ordinary tasks.
