Review and merge in the dashboard

Finish the review loop inside AgentDeck: a Review group shows done tasks whose PR waits on you, and the task page can merge the PR after a confirm (squash by default), send the task back with a note, or close the PR. A merge releases the tasks waiting on it at once. Written 2026-10-19, after the --after chain #18 → #19 → #20 sat waiting on a draft PR nobody had opened.

Why

The dashboard already shows a task like a pull request: diffs with rendered markdown, a file tree and code viewer, the runs and the plan. But acting on what you read means leaving for GitHub, and --after chains only move on a merge. Finished work also hides among the other done tasks, so nothing says "this PR is holding up two tasks".

What exists today

Area Now
PRs application/pull-requests.ts pushes and opens a PR when a task is done (pr_mode off, draft or ready) and re-reads open PRs every 3 minutes (PR_REFRESH_MS). adapters/github.ts has push, createPr and prState.
Retry The retry event already moves done → queued, the run continues on the same branch, and a retried task with an open PR pushes to that PR instead of opening another. It takes no note.
Task page Overview, Runs, Files changed, Code. The PR is a link in the sidebar.
Queue Groups by status, with "needs you" for blocked, failed and stuck tasks. Done tasks with an open PR sit under Done.

Decisions

Decision Why
Squash by default, set per repo, overridable per task One task becomes one commit on the base branch, titled after the task with the PR body as its message, and reverts in one step. Retries and plan-status commits are noise there. Run logs and the PR keep the detail. A big task with meaningful commits (a port done group by group) can use merge.
Always confirm a merge It writes to the base branch on GitHub and can't be undone from the app. The dialog shows the method, the size, the tests, any warnings and what the merge unblocks; Enter confirms, so it stays quick.
Request changes is a retry with a note, not a new status Retry already does the right thing with the branch and the open PR. The note is kept as the event's reason so the timeline shows it, and the next run's prompt includes it.
The daemon merges through gh, as it opens PRs Agents still can't push. Only a person's click (or agentdeck merge) merges.

1 · Merge from the app

Migration (the next free step): repos.merge_method TEXT NOT NULL DEFAULT 'squash' and a nullable tasks.merge_method. In domain/pull-request/, a pure mergeCheck that turns a PR's state into blocking problems (not open, conflicts) and warnings (draft, base moved on, tests failed on the last run, failing checks). In adapters/github.ts: prDetails (gh pr view --json isDraft,mergeable,mergeStateStatus,commits,additions,deletions,changedFiles,statusCheckRollup), markReady, merge(method, deleteBranch). A use case mergeTask in application/pull-requests.ts: mark a draft ready, merge, set pr_state to merged, record a task event, remove the worktree if asked, and let the scheduler tick so dependents start now. API: GET /api/tasks/:id/merge (the preview, including the tasks it unblocks) and POST /api/tasks/:id/merge with { method, delete_branch }. CLI: agentdeck merge <id> [--method squash|merge|rebase] [--yes], which prints the preview and asks unless --yes. Repo setting in the Repos panel and agentdeck repo set <repo> merge_method.

Dashboard: a Merge PR button in the task page header for a done task with an open PR. It opens a confirm dialog: the title, branch → base, the method with a menu to change it, commits (n → 1 for squash), files and lines, tests from the last run and GitHub checks, the tasks it unblocks, a "delete branch and worktree" checkbox (on), warnings above the buttons, and blocking problems disabling the merge. Enter merges, Esc cancels. Tests fake github as the PR tests do.

2 · Request changes and close

Request changes on a done task with an open PR: a note box, then the retry event with the note as its reason (POST /api/tasks/:id/retry takes an optional note; agentdeck retry <id> --note "…"). buildPrompt puts the latest note first in the next run's prompt, under "Changes requested in review". The timeline shows the note. Close PR: confirm, gh pr close, set pr_state to closed; tasks waiting on it become stuck, which the hold callout already explains.

3 · Review group

A Review state and group for done tasks with an open PR, placed after "needs you" in attention order, in both domain/task/listing.ts and its mirror app/src/taskView.ts (and agentdeck ls --status review). Within it, tasks that others wait on come first, with a chip "unblocks #19". Opening a task from the group lands on Files changed. The status bar and tray count it with the tasks that need you. The board shows it as a column between Running and Done.

Open questions

  • Should merging also pull the repo's local base branch, so the next task's worktree starts from it without a fetch?
  • Should a repo be able to auto-merge when tests and checks pass (no review), for low-risk goals?

Not in this plan

  • Line comments on the diff that become part of the request-changes note.
  • Reviewing several PRs as one stack.
