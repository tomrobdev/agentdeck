Merge requests and the activity list

Merge in the dashboard stops waiting on GitHub. It records a merge request, the dialog closes at once, and the daemon merges the PR when it is ready: after its checks pass, after a sync settles a conflict, after the PRs it lands after. A pill in the status bar counts everything under way, and opens a list of it.

Why

  • app/src/components/task/MergeDialog.vue and app/src/components/task/BulkMergeDialog.vue wait on api.merge and api.mergeAll. The bulk dialog can't be closed while it merges (close does nothing while running), and a PR whose checks are still running can only be merged now or later by hand.
  • The daemon already merges on its own. refreshPrStates (daemon/src/application/pull-request/pull-requests.ts) reads every open PR, the scheduler syncs the conflicting ones (resolveConflicting in daemon/src/application/sync.ts) and merges one ready PR per refresh (autoMerge in daemon/src/application/pull-request/auto-merge.ts). A merge asks for a re-read (db.requestPrCheck()), so the next one follows at once.
  • But auto-merge's check (autoMergeCheck in daemon/src/domain/pull-request/auto-merge.ts) stands in for a person: it wants a label and stays under line limits and skipped paths. A person who pressed Merge has looked; those rules don't apply to them.
  • Nothing in the window says what is under way unless that task's row is on screen.

Decisions

  • Merge request is the new word: a person's Merge, which the daemon carries out once the PR is ready. Not "approve", which is what a person does to a proposal. Add it to the domain language in CLAUDE.md.
  • A merge request waits for checks still running, a conflict being synced, mergeability GitHub hasn't worked out and the PRs it lands after. It is dropped, with a notification saying why, when a check fails, the last run's tests failed, branch protection blocks it or the PR is no longer open. A paused daemon or repo doesn't hold it: a person asked.
  • When the dialog already shows failing checks or failed tests, its button is "Merge now" and merges at once, as today: the person waves those through there and then.
  • A requested merge deletes the remote branch and the worktree, as auto-merge and Merge all do, so the dialog's checkbox goes.
  • agentdeck merge in the CLI keeps merging at once.

Record a merge request

  • Add to tasks: merge_requested_at (UTC text, null when there is no request), merge_request_method and merge_request_check (the last check's JSON, as auto_merge_check holds auto-merge's). Follow the migration rule in CLAUDE.md.
  • In daemon/src/domain/pull-request/merge-request.ts (pure), mergeRequestCheck: the decisions above as a verdict over mergeFindings, returning the same AutoMergeCheck shape (merge, wait or never, with reasons). A draft or a branch behind the base is fine, as for auto-merge.
  • Use cases in daemon/src/application/pull-request/merge-requests.ts, exported through daemon/src/application/actions.ts: requestMerge(db, id, { method }) (a done task with an open PR; the method defaults to the task's, then the repo's), requestMerges(db, { ids }) for Merge all, returning the ones it could not request and why, and cancelMergeRequest(db, id). Requesting asks for a PR re-read (db.requestPrCheck()).
  • mergePreview gains request: what mergeRequestCheck says now, so the dialog can pick its button.
  • Routes beside the merge routes in daemon/src/api/routes/tasks.ts: POST and DELETE /api/tasks/:id/merge-request, and POST /api/tasks/merge-requests with { ids }. Add the types to daemon/src/api/contract.ts and daemon/src/api/contract-check.ts.
  • recordMerge clears the request.
  • A domain test in daemon/test/merge-request.test.ts gives each finding its verdict: pending checks, a conflict, lands after and unknown mergeability wait; a failing check, failed tests, branch protection and a closed PR are never; a draft or a branch behind the base merges; an auto-merge limit (lines, skipped paths, no label) doesn't count.
  • A test with a db fixture shows requestMerge refusing a task that isn't done or has no open PR, and cancelMergeRequest clearing the request.
  • pnpm db:check and pnpm check pass, and the migration's hash is in daemon/test/migrations.lock.

The daemon carries out merge requests

  • In refreshPrStates, a task with a merge request gets mergeRequestCheck instead of the auto-merge check, and keeps it in merge_request_check. merge puts it in found.mergeable, ahead of auto-merges. never clears the request, logs it, and sends a notification ("Could not merge #12: 1 check failing") as autoMerge does for a failed merge. A conflict goes to found.conflicting as now, so it is synced.
  • A request whose task is no longer done, or whose PR is no longer open, is cleared by the refresh.
  • autoMerge merges a requested PR with the request's method, recorded with the reason requested (squash).
  • While a request waits on running checks or on mergeability GitHub hasn't worked out, the scheduler reads the PRs again after 30 seconds rather than the usual 3 minutes (maybeRefreshPrs in daemon/src/application/scheduler/scheduler.ts).
  • A lock in the merge use case says which task is merging right now, as isSyncLocked does for syncs.
  • TaskSummary gains merge_request: null with no request, else { state: 'waiting' | 'merging', method, reasons, since }, decided in the domain and filled in daemon/src/application/task/task-views.ts without a query per task.
  • Tests with a db fixture and a fake GitHub, in the style of daemon/test/auto-merge.test.ts: a request with checks running waits, then merges once they pass; a request whose check fails is cleared with a notification; a request over auto-merge's line limit merges; two requests where one lands after the other merge in that order.
  • A domain test covers the merge_request view: none, waiting with its reasons, and merging.
  • pnpm check passes.

Merge in the dashboard requests the merge

  • In MergeDialog.vue, the button requests the merge and closes the dialog at once. It reads "Merge" when the preview's request says merge, and "Merge when ready" when it waits, with the reasons listed above it. When it says never because of failing checks or failed tests, the button is "Merge now" and calls api.merge as today. The delete-branch checkbox goes.
  • In BulkMergeDialog.vue, "Merge n" requests them all and closes. The tasks it could not request stay listed with why. The sync buttons and "Merge the n synced" go: the daemon syncs a conflicting PR it has a request for.
  • List rows (ListView.vue), board cards (BoardView.vue) and the task header (TaskActions.vue) show the request: "Merging when ready · 2 checks running", or "Merging…". Word it in app/src/api/format.ts.
  • A task with a request offers "Cancel merge" in its row menu (RowMenu.vue) and its header, and its Merge stays disabled.
  • In the dashboard against a daemon, Merge on a PR with checks running closes the dialog at once, the row says it waits for the checks, and the PR merges without another click once they pass.
  • Merge all closes at once, and the PRs merge one after another.
  • Cancel merge clears the request, and the row goes back to its usual state.
  • pnpm check passes.

The activity pill in the status bar

  • In app/src/components/layout/StatusBar.vue, beside the slots: a spinner and "n active" whenever anything is under way, and nothing when nothing is. It counts running tasks (running and cancel_requested), syncs (TaskSummary.sync), merge requests (TaskSummary.merge_request) and planner runs.
  • The daemon doesn't tell the dashboard which planner runs are under way: add planning to Status, one entry per unfinished planner run with its repo and start.
  • Clicking the pill opens a list (app/src/components/ui/Popover.vue): for each, its kind, #id and title, what it is doing in the words the rows use (describeLive, describeSync, the merge request's wording), and for how long. A row opens the task, on Runs for a run or a resolve run. A merge request's row has Cancel merge.
  • Build the list in a composable, app/src/composables/useActivity.ts, from the task list and the status the window already reads; no new polling.
  • In the dashboard with one task running and one merge request waiting, the status bar shows a spinner and "2 active", and the list shows both with what each is doing.
  • Clicking the running task's row opens it on Runs. With nothing under way, the pill is gone.
  • pnpm check passes.

Out of scope

  • The auto-merge rules, and how a sync or resolve run works.
  • Merge requests from the CLI; agentdeck merge stays as it is.
  • GitHub's own merge queue and auto-merge.
  • Interactive claude sessions outside the daemon (a terminal running /add-task): the daemon doesn't know of them.
