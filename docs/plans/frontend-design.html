Front-end design: audit, themes, Tailwind

Give the dashboard one design system: audit what the styles do today, try several themes with a switcher that includes a light mode you can pick by hand, then port the components to Tailwind on top of the chosen theme tokens. Three tasks, run in order. Written 2026-10-19.

Why

The dashboard grew fast through the dashboard-views work: 28 components carry about 1,950 lines of scoped CSS on top of a 275-line style.css. The colours are tokens, but spacing, type sizes, radii and shadows are written by hand in each component, so the same row or chip looks slightly different across views. Light or dark follows the system only: there is no way to choose, and no second theme to try.

What exists today

Area Now
Stack Vue 3.5 + Vite 8 in Tauri 2. markdown-it, DOMPurify and highlight.js. No CSS framework or preprocessor.
Tokens app/src/style.css: 16 colour tokens (surfaces, text, accent, one per task status) plus --radius, redefined under prefers-color-scheme: dark. Highlight colours are --hl-*. Components use them well (--border 55 times, --muted 43); only two hard-coded hex values remain.
Per-component CSS Scoped <style> blocks in every component; callouts and chips are restyled in several places.
Theme choice None. The system setting decides, and the plan frame (PlanCard.vue) follows it separately.

Decisions

Decision Why
Themes before Tailwind, not after The port bakes token names into every class. Settling the token set first (step 2) makes the port mechanical, and a theme can be tried without touching component markup, since the components already read CSS variables.
Themes are sets of CSS variables, picked with data-theme on <html> No rebuild and no class churn: switching rewrites one attribute. "System" stays the default and maps to the light or dark variant of the chosen theme. The choice is kept in localStorage, which is fine for a per-machine preference.
Tailwind v4 through @tailwindcss/vite, as a dev dependency It compiles to plain CSS at build time, so the shipped app gains no runtime dependency (CLAUDE.md). v4's @theme maps utilities straight onto our CSS variables, so the themes from step 2 keep working unchanged.
Port component by component, with the old scoped CSS deleted as each one moves Each commit stays reviewable and the app works between them. Nothing is left half in both systems at the end.

1 · Audit the stack

Read every component and style.css and write docs/frontend-audit.md. It lists the stack and versions; the token inventory and where tokens are missing (spacing, type scale, radii, shadows, z-index); repeated patterns that should be one component or one utility (callouts, chips, pills, buttons, tables, popovers); hard-coded values; contrast problems in light and dark (WCAG AA for text); and anything that blocks a Tailwind v4 port or a theme switch. End with a proposed token set that steps 2 and 3 use. Docs only: no code changes.

2 · Prototype themes and the switcher

Using the audit's token set, add three or four clearly different themes, each with a light and a dark variant, in app/src/themes.css (e.g. the current warm neutral, a cool Linear-like grey, a high-contrast one, a GitHub-like one). Add a theme menu to Settings and a quick toggle in the status bar: theme, and mode (system, light, dark). Apply it with data-theme and data-mode on <html>, keep it in localStorage, and pass the mode to the plan frame so plans follow it. Use the prototype skill's UI approach where it helps: switching must be instant so themes can be compared side by side on real data. Every theme must pass AA contrast for text, status colours and code highlighting in both modes. Leave the current theme as the default; the person picks the final default after trying them.

3 · Port to Tailwind

Add Tailwind v4 with @tailwindcss/vite. Map the theme tokens in @theme so utilities such as bg-panel, text-muted and border-border read the CSS variables, and define the dark variant from data-mode, not the media query. Port the components one group at a time (shell and status bar, queue, task page, files, modals), deleting each one's scoped CSS as it moves; keep in CSS only what utilities can't express (highlight.js classes, the diff grid, markdown output). Pull repeated patterns the audit found into small components or @utility rules. Check every view in both modes and every theme; the app must look the same as before, apart from fixes the audit called for. pnpm check must pass.

Open questions

  • Which theme becomes the default? Decided by the person after step 2.
  • Should the theme follow the user to the CLI's colours, or to plan pages agents write?

Not in this plan

  • A component library (Reka UI, PrimeVue): not needed for this size of app.
  • User-defined custom themes.
  • Redesigning layouts: this plan changes how styles are written, not what the views show.
