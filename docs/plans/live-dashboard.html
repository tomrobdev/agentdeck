Live dashboard: a change stream and TanStack Query

The dashboard polls /api/status and the task list or task every 2 s, forever, even hidden in the tray, and diffs each answer with JSON.stringify so nothing re-renders. Every panel fetches on its own and every action refetches everything. Replace that with two pieces: the daemon tells the dashboard when the database changed (an SSE stream of a revision number, read from SQLite's own change counters so CLI writes count too), and the dashboard keeps its server data in TanStack Query and refetches what is on screen when the revision moves. Written 2026-11-01.

Decisions

  • A revision, not topics. The stream sends one number that moves whenever the database changed. The dashboard has two or three queries on screen at a time, so refetching all of them is simpler than tracking which table changed, and a change made by the CLI can't say which table it touched anyway.
  • The revision comes from SQLite, not from the stores. PRAGMA data_version moves when another connection commits (the CLI, another process); total_changes() counts rows written on the daemon's own connection. Reading both every 250 ms costs two trivial queries and needs no hook in any store. An UPDATE that matches no row changes neither.
  • The database stays the only shared state. The watcher is an instance made in daemon.ts and handed to the API and the scheduler, not module state.
  • The scheduler wakes on other processes' writes only (data_version), so a change made with the CLI starts work at once instead of at the next 5 s tick. Not on its own writes: a tick writes, and waking on that would loop.
  • TanStack Query (@tanstack/vue-query) is the one new dependency. It is added to app/package.json on main with this plan, because workers can't install packages. The reason: it replaces the poll loop, the keep() diffing, the per-panel loading and error handling and the refetch-everything after actions with one cache keyed by what was asked, and shows the cached task while it refetches instead of "Loading task #N…". No Pinia: once Query holds the server data, what is left (route, modal, toast, selection) is a few refs.
  • Query keys and query options live in app/src/api/queries.ts, next to the calls they wrap, so a component asks for taskQuery(id), never builds a key by hand.

Change stream: /api/events

db: a small store, db/changes.ts, merged into Db in db/index.ts, with changeCounters(): { dataVersion: number; ownChanges: number } reading PRAGMA data_version and SELECT total_changes() on the daemon's connection. There is no table to build on, so this is one of the places raw SQL is right; say so in a comment.

application: application/changes.ts exports a class ChangeWatcher. Constructed with the Db; start(intervalMs = 250) reads the counters on an unref'd timer and, when either moved, bumps rev (starting at 1) and calls every subscriber with it; subscribe(fn) returns an unsubscribe; onOtherProcess(fn) is called only when dataVersion moved; stop(). actions.ts re-exports it so the API can name the type.

API: ApiContext gets changes: Pick<ChangeWatcher, 'rev' | 'subscribe'> (an idle default in server.ts, as for the scheduler). GET /api/events in api/routes/daemon.ts answers text/event-stream, writes event: rev with {"rev": n} at once and on every change, a : ping comment every 25 s, and unsubscribes when the request closes. Same CORS as the rest (it goes through dispatch, like the log stream). Add the event's shape to api/contract.ts.

Composition: daemon.ts makes the watcher (not in once mode), passes it to startApi, wires onOtherProcess(() => scheduler.wake()), and stops it on exit.

  • pnpm check:fast passes.
  • Tests: a write through a second DatabaseSync on the same file (a CLI) moves rev and calls onOtherProcess; a write through the daemon's own Db moves rev but doesn't call onOtherProcess; with no writes, rev stays put across several intervals.
  • API test: GET /api/events answers text/event-stream with the current rev first, then a new rev after a write; closing the request removes the subscriber.
  • docs/architecture.md is regenerated (pnpm docs) and the architecture test passes.

Dashboard on TanStack Query: status, task list, task, repos

@tanstack/vue-query is already in app/package.json. main.ts installs VueQueryPlugin with one QueryClient: retry: false for ApiError('offline') (the offline screen handles it), refetchOnWindowFocus: true.

New app/src/api/queries.ts: keys and queryOptions for status, tasks, task(id) and repos, re-exported from api/index.ts. In App.vue, replace refresh(), keep(), lastJson and the interval with useQuery: status always, the list only on the queue, the task only on a task page, repos always. Status and the open page's query keep a 2 s refetchInterval for now (the stream step removes it); status also polls in the background, because the tray label (setTrayStatus) reads it while the window is hidden; the others don't. offline comes from the status query's error.

Opening a task shows the cached task at once, if there is one, while it refetches; "Loading task #N…" only when there is none. useActions keeps its interface; its refresh becomes queryClient.invalidateQueries(), which also refetches repos, so refreshAfterAction goes.

  • pnpm check:fast passes, and pnpm --filter agentdeck-app exec vite build builds.
  • keep, lastJson and POLL_MS's setInterval are gone from App.vue.
  • Going back to a task already opened shows it with no loading screen.
  • Stopping the daemon still shows the offline screen, and starting it again reconnects with no reload.

The rest of the dashboard's reads on Query

Every read that a component does on its own moves to a query in api/queries.ts: ReposPanel (repo, archivedRepos, repoDeletion), SettingsPanel (settings, service), MergeDialog (mergePreview), DependenciesCard (its task list, sharing the tasks key), NeedsCallout (repo), PlanCard (planHtml), CodeTab, ChangesTab, DocumentsCard and SnippetPopover (tree, file, diff), and useChanges (changes). Each component drops its own loading/error refs for the query's.

File, tree and diff reads at a commit never change: staleTime: Infinity for those keyed by commit. useChanges keeps its 10 s refetch while the task is running (a run commits without touching the database) and keeps returning the same object while head and base are unchanged. Writes stay on useActions().run; no useMutation in this step.

  • pnpm check:fast passes, and pnpm --filter agentdeck-app exec vite build builds.
  • No component under app/src/components/ calls a read in api directly (only api/queries.ts does); writes and logUrl stay as they are.
  • Reopening a file or diff already seen shows it at once, with no request.

Refresh from the change stream; drop the 2 s poll

A composable, composables/useChangeStream.ts, used once in App.vue: an EventSource on API_BASE + '/api/events'. On a rev event that differs from the last one, and on every (re)open (a daemon restart reconnects), queryClient.invalidateQueries(), which refetches only the queries on screen. Closed on unmount.

Remove the 2 s refetchIntervals from query-core. Keep a 30 s fallback on status only, in the background too: a governor hold lifting and other waits change with time, not with a write. useChanges' 10 s refetch while running stays. The CSP in tauri.conf.json already allows http://127.0.0.1:4317; check that the stream connects in the built app, not only in the browser.

  • pnpm check:fast passes, and pnpm --filter agentdeck-app exec vite build builds.
  • With the dashboard idle on the queue, the network panel shows the one event stream and no other request for 25 s (until the 30 s status fallback).
  • agentdeck add from a terminal shows the new task in the queue within a second.
  • Restarting the daemon (agentdeck restart) reconnects the stream and the data with no reload.
