One start decision, slots counted in the db

Whether new work may start is decided twice: queueWait in domain/task/start.ts, and Scheduler.gate(), which re-derives paused, rate limited and the governor with its own strings and clock, kept in step only by a "mirrors" comment. Slots are counted three ways: the scheduler's in-memory running set (tasks, the planner and the conflict loop), countRunning() + syncing.size in canStartResolve, and countRunning() alone in startWaits. Make the domain decide once, and count slots from the db so the daemon, the API and the CLI all see the same number. Written 2026-10-25.

Decisions

Decision Why
domain/task/start.ts gets startDecision(q: QueueState, o: { ignorePause: boolean; used: number; now: number }): { wait: QueueWait | null; free: number } and describeWait(w: QueueWait): string (the log and reason text the scheduler writes today). free is max(0, max_concurrent - used), and 0 whenever wait is set. queueWait becomes a private helper or is replaced. One pure decision with the clock passed in, testable without a scheduler.
A slot is taken by: a task in running or cancel_requested; a resolve run that has not ended (runs.kind = 'resolve' AND ended_at IS NULL) for a task that is not itself running; a planner run that has not ended. A clean sync of a done task takes no slot: it runs no claude. db gets one query, slotsUsed(): number, that counts exactly this. Every claude process holds a slot and nothing else does. The db is the one place every process can read, which makes the module-level syncing set unnecessary for counting.
The planner keeps taking a slot, as it does today through the scheduler's running set. Say so in the startDecision doc comment. No change of behaviour in this task.
The scheduler keeps only what is its own: edge-detecting a hold to log and notify it once, and the in-memory set of promises it awaits on stop() and in once mode. It no longer uses that set to count slots. Announcing a hold is the scheduler's job; deciding one is the domain's.
The syncing set in sync.ts stays only as the per-task lock ("one sync at a time per task") and isSyncing keeps its meaning. That lock is a different concern from slot counting.

One start decision in the domain

Add startDecision and describeWait to domain/task/start.ts with tests for each wait kind, the ignorePause case (run-once) and the free-slot arithmetic. Make Scheduler.gate(), canStartResolve (sync.ts) and startWaits/queueWaits (queue.ts) call it.

  • The "Mirrors the scheduler's gate" comment and the scheduler's own paused / rate-limited / governor checks are gone.
  • The scheduler's log lines for a hold, a rate limit and a pause read as they do today.
  • Domain tests cover every QueueWait kind and free.

Slots counted in the db

Add slotsUsed() to the db (in db/runs.ts or db/tasks.ts), and use it in the scheduler's start loop, canStartResolve and startWaits. Check EXPLAIN QUERY PLAN uses an index, as the other run queries' tests do.

  • A test: with max_concurrent 2, one running task and one open resolve run, no further task is claimed and startWaits reports slots 2/2.
  • A test: a running task whose sync started a resolve run counts once, not twice.
  • countRunning() + syncing.size no longer appears anywhere.
