Fewer blocked tasks

Most blocks so far came from the environment, not the task: a package the sandbox couldn't install (#20), a port or ps it refused (#34), a file under .claude/ a worker may not edit (#37). Each cost an attempt and a round trip through a person, who had to read the run's text to find what was needed. Let a worker say what it needs in a form the daemon reads, give the attempt back when the environment is to blame, and turn the commonest need, a new dependency, into one click. Written 2026-10-25.

Already done

  • Sandboxed workers may bind localhost ports (f97209c).
  • A test that fails only because of the sandbox no longer blocks: the worker finishes and the daemon's own test run decides (21e4103).
  • The delegate skill tells the person queueing about dependencies, network hosts and .claude/ (c075eaa).

Decisions

Decision Why
A worker that needs something states it on its STATUS line: STATUS: BLOCKED: NEEDS deps: tailwindcss @tailwindcss/vite, NEEDS host: registry.example.com, NEEDS edit: .claude/skills/x/SKILL.md. Three kinds, nothing else. The daemon already parses that line. A fixed form is something the dashboard can act on; free text isn't.
A block is the environment's fault when the worker said NEEDS, or the run had permission denials, or setup failed. Then the attempt is given back, as rate_limited does. Retrying after the environment is fixed shouldn't use up the task's attempts, or raise its limit (#34 ended at 4/4).
Dependencies are installed only when a person asks, never on the worker's say-so. The daemon runs the repo's package manager outside the sandbox in the task's worktree, commits the manifest and lockfile on the task's branch, and requeues the task. Installing what an agent names is a supply-chain risk; one click with the package names in front of you keeps a person on it. Node toolchains (pnpm, yarn, npm) first; other toolchains show the request and leave the install to the person.
Allowing a host is the repo's network setting, changed only from the person's click, with the host shown. It widens what every future worker of that repo can reach.

Workers state what they need; environment blocks give the attempt back

domain/run/run.ts: parseStatus also returns needs: { kind: 'deps' | 'host' | 'edit'; items: string[] } when the reason starts with NEEDS. domain/run/prompt.ts: the worker system prompt describes the three forms in one short paragraph. A pure isEnvironmentBlock (needs, denials, or a setup failure). Migration step: tasks.needs TEXT (JSON or null), set when a run blocks with needs, cleared when the task is queued again. domain/task/lifecycle.ts: the blocked finish event can carry environment: true, and applyEvent then gives the attempt back. application/worker.ts passes it. The timeline says "blocked by the environment; attempt given back". Mirror needs in db/tables.ts, the Task type and app/src/api.ts.

  • pnpm check passes, including pnpm db:check.
  • Tests: each NEEDS form parses; a plain BLOCKED reason has no needs; an environment block leaves attempts where it was before the run; a task-caused block uses its attempt.
  • agentdeck show prints the needs of a blocked task.

Install requested dependencies on request

application/tasks.ts: installNeeds(id), for a blocked task whose needs are deps and whose repo's toolchain is pnpm, yarn or npm. It checks each name is a valid npm package spec, runs the toolchain's add command (pnpm add -D or the plain form, per a --dev flag the request may carry) in the task's worktree through the shell adapter, outside the sandbox, commits package.json and the lockfile ("agentdeck: add … for task #id"), and retries the task with a note naming what was installed. Failure leaves the task blocked with the installer's last line. API: POST /api/tasks/:id/install-needs. CLI: agentdeck install-needs <id>, which prints the packages and asks unless --yes.

  • pnpm check passes.
  • Tests, with a fake package manager: names are validated (a shell metacharacter is refused); the commit holds only the manifest and lockfile; the task is queued again with the note; a failed install keeps it blocked.
  • Nothing installs without the person's request: no code path calls installNeeds from the worker or scheduler.

Show the need, and the one action that clears it

On a blocked task's page, a callout above the timeline names what the worker needs. deps: the packages and "Install and retry" (or, for a non-Node toolchain, "Install them on the branch, then Retry"). host: the host and "Allow for <repo> and retry", which asks for confirmation first. edit: the file and the worker's text, and Retry for after you've made the edit. The queue row of a task with needs shows a small "needs" chip.

  • pnpm check passes.
  • Each of the three kinds renders its own action; a block without needs shows no callout.
  • "Allow" names the host and the repo in its confirmation.

Not in this plan

  • Installing without a person (see Decisions).
  • A sandbox check in repo doctor: with sandbox-only test failures no longer blocking, what's left is task-specific.
  • Retrying every task a single fix unblocks at once.
