Auto-merge done tasks

Let the daemon merge a done task's PR without a person, when the repo or the task says so and a strict check passes: green CI, passing tests, no conflicts, small enough, no protected paths. The daemon does the merge itself on its PR refresh, reusing mergeTask, so it works on any repo, not only those with GitHub branch protection. The PR carries an agentdeck:auto-merge label so GitHub shows it, and removing the label opts that PR out. Written 2026-11-01.

Why

Every done task waits for a person to press merge, and --after chains don't move until they do. For small, tested changes that wait adds nothing. GitHub's own auto-merge (gh pr merge --auto) only works on repos with "Allow auto-merge" turned on and required status checks, and not on drafts. AgentDeck has to work on any repo, so the daemon decides and merges.

What exists today

Area Now
Merge mergeTask (application/pull-request/pull-requests.ts) reads the PR, runs mergeCheck, marks a draft ready, merges with the task's or repo's merge_method, records it, asks for a PR re-read, and can delete the branch and worktree. The tasks waiting on it start on the next tick.
Check mergeCheck (domain/pull-request/merge.ts) returns problems (not open, conflicting) and warnings (draft, behind, blocked, failing tests, failing or pending checks). A person sees the warnings and decides.
Refresh The scheduler calls refreshPrStates every PR_REFRESH_MS, and at once after a merge. It reads each open PR of a done task and hands conflicting ones to resolveConflicting.
Tests A work run records tests_passed. A sync started by the daemon or a person (sync.ts) runs the tests after a resolve run and records them too.
Repo flags auto_approve (planner proposals skip approval) and auto_resolve follow the same path through db/repos.ts, repo/repos.ts, settings.ts (repo set), api/contract.ts and app/src/lib/forms.ts. Auto-merge follows the same path.

Decisions

Decision Why
The daemon merges, on its PR refresh It works on any repo and reuses mergeTask's merge and cleanup. It only merges while the daemon is running, which is fine: nothing else moves then either.
Off by default. Set per repo, with a per-task override Like merge_method. tasks.auto_merge is NULL (use the repo's), 0 or 1, so you can turn it on for one task in a cautious repo, or off for one risky task.
Planner proposals count only if a person approved them A source = 'planner' task is eligible only when the repo has auto_approve off, so a person queued it. Otherwise no person would have seen the work before it reached the base branch. An explicit tasks.auto_merge = 1 still wins.
Every mergeCheck warning blocks A person can wave a warning through. The daemon can't, so a warning means "wait" (pending checks, BEHIND) or "leave it for a person" (failing checks, failing tests, protection blocking).
Something has to have tested it The last run that ran tests must have passed. If the repo has no test_cmd, it needs at least one CI check, all green. A repo with neither is never auto-merged, and its settings page says why.
A sync doesn't stop it A sync started by the daemon runs the tests after a resolve run and records the result, so a branch that got a resolve run is judged by those tests and by CI on the new commit.
Limits: lines changed and protected paths auto_merge_max_lines (additions + deletions, default 400) and auto_merge_skip, path prefixes that need a person (default [".github/"]). Prefix matching keeps domain/ free of a glob library.
A paused repo or daemon doesn't auto-merge Paused means nothing moves on its own. A governor hold doesn't apply: a merge uses no quota.
The branch and worktree are cleaned up delete_branch: true. The local branch stays, as with a person's merge, so the diff can still be read.

The rule

A done task's open PR is auto-merged when all of these hold:

  1. Auto-merge is on: task.auto_merge ?? repo.auto_merge, and for a planner task with auto_merge NULL, the repo has auto_approve off.
  2. The PR has the agentdeck:auto-merge label (step 4).
  3. The PR is open and merges cleanly, with no checks failing or pending and nothing blocking it. A draft is fine (mergeTask marks it ready). BEHIND is fine too: a PR that merges cleanly onto the moved base is what GitHub would merge, and a repo that requires up-to-date branches makes gh pr merge fail, which is told once.
  4. The last tested run passed, or the repo has no test_cmd and the PR has at least one check.
  5. additions + deletions ≤ auto_merge_max_lines, and no changed file starts with a prefix in auto_merge_skip.
  6. Neither the repo nor the daemon is paused.

The check returns { verdict: 'merge' | 'wait' | 'never', reasons: string[] }. wait is for what can still change on its own (checks pending, mergeability unknown, a conflict waiting for a sync, a pause). never is for what needs a person (failing checks or tests, too big, protected path, no tests at all, no label, GitHub listing fewer files than changed). The merge dialog shows the reasons.

1 · The auto-merge check

domain/pull-request/auto-merge.ts: autoMergeOn(task, repo) says whether auto-merge is on, and autoMergeCheck gives the verdict from the repo's limits and test_cmd, the PrDetails, the last tested run's tests_passed, and why anything is paused. Extend PrDetails with paths: string[] and labels: string[], which parsePrDetails reads from files and labels. Add both fields to the gh pr view call in adapters/github.ts.

  • autoMergeCheck is pure and unit-tested for each verdict and each reason.
  • A planner task under auto_approve gets never unless its own flag is 1.
  • pnpm test and pnpm typecheck pass.

3 · The daemon merges

refreshPrStates already reads prDetails for every open PR of a done task. For one that isn't conflicting, it also runs the check (autoMergeFor) and puts the task in a new PrRefresh.mergeable: number[] list when the verdict is merge. The scheduler hands the list to autoMerge in pull-request/auto-merge.ts, inside the refresh so two refreshes never merge at once. It merges the first ready PR with the details the refresh just read, through mergeOpenPr (split out of mergeTask), with the repo's method and the branch and worktree removed. One merge per refresh: it moves the base, and the re-read it asks for picks up the next PR once GitHub has worked out its mergeability. prDetails reads the changed files and labels only for tasks with auto-merge on.

recordMerge gets a reason of auto-merged (squash) so the task's events show who merged it. A new merged notify kind tells the person. It is on by default for a new install; an existing one adds it to notify_events (Settings → PR auto-merged). A merge that fails is logged and notified once per task and error. autoMerge does all of its own telling; the scheduler keeps the last error per task in memory and passes it in, so a failure doesn't notify every 3 minutes (a restart tells it once more). The wait and never verdicts don't notify.

  • A test with a fake github checks that an eligible PR is merged and the waiting task starts.
  • An ineligible PR (failing check, too big, protected path, planner under auto_approve) is left open.
  • Two eligible PRs in one repo merge one after the other, never against the same stale base.

4 · The GitHub label

When openPr opens a PR for a task with auto-merge on, it passes --label agentdeck:auto-merge. First it runs gh label create agentdeck:auto-merge --force once per repo, which is idempotent, because gh pr create fails on a missing label. The rule needs the label, so it fails closed: if the label can't be created (permissions), the PR still opens without it and waits for a person. Removing the label on GitHub opts that PR out. The task's setting stays as it was, and the merge dialog says the label is missing. Turning auto-merge on or off for one task (step 5) adds or removes the label on its open PR. A PR opened before the repo turned auto-merge on gets the label that way.

  • A new PR in an auto-merge repo carries the label. Without it the PR is never auto-merged.
  • A failure to create the label doesn't stop the PR from opening.

5 · CLI, API and dashboard

  • CLI: agentdeck repo set <repo> auto_merge on|off, auto_merge_max_lines <n> and auto_merge_skip "<prefix>,…" in settings.ts and cli/help.ts, and agentdeck auto-merge <id> on|off|repo for one task.
  • API: the repo update body takes the three fields. POST /api/tasks/:id/auto-merge with { auto_merge: true | false | null } (setAutoMerge), since editTask refuses a done task. The merge preview (GET /api/tasks/:id/merge) gets auto_merge: { verdict, reasons } | null, read from GitHub like the rest of the preview.
  • Dashboard: an auto-merge toggle with the limits in the repo form (lib/forms.ts). An Auto-merge select in the task sidebar (the repo's setting, on, off). The merge dialog has an Auto-merge line: "on; waiting: 2 checks still running on GitHub" or "needs you: touches .github/workflows/ci.yml". A person can always merge sooner.
  • api/contract-check.ts passes. The repo form and task sidebar show and change the setting.

Open questions

  • Should auto-merge wait a grace period after a task is done (say 10 minutes) so a person can look first? Cheap to add as auto_merge_delay. Left out until it's needed.
  • The reasons only show in the merge dialog, which reads GitHub. Showing them on the task page without opening it would need the refresh to store the last verdict on the task.
  • The sidebar's "The repo's setting" doesn't say whether the repo has auto-merge on.
  • Is 400 lines the right default, or should it count files too?

Not in this plan

  • Passing gh pr merge --auto too on repos with required checks, so GitHub merges without waiting for the refresh.
  • Merge queues, and waiting on approving reviews.
  • Reverting an auto-merged task when the base branch's CI fails afterwards.
