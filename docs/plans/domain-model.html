Tighten the domain model

An audit of daemon/src/domain found it pure but thin. The Task's rules are split between domain/ (next status), SQL (what each event does to attempts, reasons and needs) and application/ (input rules). Derived states such as "review" and "stuck" are written out in four places. And the code's words drift from the domain language in CLAUDE.md, which now settles them: proposals, not plans, for the planner; sync for bringing the base branch in; hold only for the governor; stop reason for why a task ended blocked or failed. Rename to that language, move each rule into the domain once, and share the derived states with the dashboard. Written 2026-10-25.

Decisions

Decision Why
The words in CLAUDE.md's Domain language are the names in code, logs, the CLI and the dashboard. User-facing commands and API paths that change name keep the old one working: agentdeck repo plan and agentdeck resolve stay as aliases, and API paths stay as they are. The language was settled on 2026-10-25. Aliases keep scripts, the delegate skill and muscle memory working.
A domain rule returns a result or an error message, as validateBudget does; the use case turns the message into an ActionError. The rule can be tested without a database, and the CLI and API share it.
Typed domain models (booleans, arrays, a PullRequest value) and a typed pause cause are not in this plan; see the end. They change the row-to-model mapping that the Drizzle plan's foundation step rebuilds, and the ticket-source design for Plane.

Rename to the domain language (no schema change)

Proposals: domain/planner/plan.ts → domain/planner/proposals.ts; PlanResult → ProposalResult; planNow → proposeNow, planRepo → propose, the planning sets and flags → proposing; new planner logs are named proposals-<repo>-….jsonl. agentdeck repo propose, with repo plan kept as an alias. Dashboard labels say "Propose tasks".

Sync: application/conflicts.ts → application/sync.ts; bringInBase → syncBranch, BringInResult → SyncResult, resolveTask (a person asking) → syncNow; the resolve run keeps its name. syncSummary and conflictReason move from domain/pull-request/conflict.ts to domain/branch/sync.ts (syncing happens with PRs off too); isConflicting and isMergeabilityUnknown stay with the PR. agentdeck sync <id>, with resolve kept as an alias. The dashboard's button and messages say sync.

Moves: Needs, parseNeeds and readNeeds from domain/run/run.ts to domain/task/needs.ts (a task holds them). PROMPT_SECTIONS from the planner module to domain/task/task.ts (every task prompt uses them; the delegate skill's reference to its location is updated by a person, since workers can't edit .claude/: note it in the PR). lastLine from domain/run/run.ts to a domain/text.ts. Update CLAUDE.md's Boundaries paragraph for the moved and renamed files.

  • pnpm check passes.
  • Outside comments that explain the change, no identifier in daemon/src or app/src names the planner's output a plan (grep planNow, PlanResult, planRepo), or the sync bringInBase or resolveTask.
  • Tests: agentdeck repo plan and agentdeck resolve still run their commands.

Stop reason and paused, where they are stored

Stop reason: a migration step renames tasks.blocked_reason to stop_reason (ALTER TABLE … RENAME COLUMN), mirrored in db/tables.ts, Task, api/contract.ts, the dashboard, the CLI and the listing's search. Remove the "until that column is renamed" note from CLAUDE.md.

Paused, not held: a paused repo notifies with a new kind paused instead of hold (application/pause.ts); hold stays for the governor. A migration step adds paused to a stored notify_events setting that has hold, so nobody loses those notifications. The settings UI lists both kinds. In domain/task/start.ts, QueueHold → QueueWait and StartHold → StartWait (what a queued task waits for: a hold, a pause, a dependency or a slot); the API's hold field on tasks and status becomes wait, mirrored in the contract and the dashboard.

  • pnpm check passes, including pnpm db:check.
  • Migration tests: an existing blocked_reason value survives as stop_reason; a notify_events of done,hold becomes done,hold,paused, and one without hold is unchanged.
  • Test: pausing a repo records a paused notification; a governor hold still records hold.

What each lifecycle event does, decided in the domain

domain/task/lifecycle.ts: a pure transition(task, event, opts) → { to, changes, history } | null. changes holds the new values of every field the event sets: attempts, max_attempts, restarts, stop_reason, needs, done_by. history is the timeline type (for example environment_block). It takes over every rule now in the sets builder of applyEvent (db/tasks.ts), which keeps only the persisting: UPDATE … WHERE id = ? AND status = ?, also guarded on each counter the changes were computed from (attempts, restarts), retried as today when the guard misses. Behaviour stays exactly the same.

  • pnpm check passes; the existing lifecycle, event and mark-done tests pass unchanged.
  • New table-driven tests call transition with no database, one case per rule key, checking the status, every change and the history type, including the cancel-wins rule from cancel_requested.
  • applyEvent has no condition on the event's type left (grep event.type in db/tasks.ts).

One definition of a task's stage, shared with the dashboard

New domain/task/stage.ts, importing types only: hasOpenPr, isReview, isMerged, isWaiting, isStuck, STATUS_GROUPS and statusGroup, moved from app/src/boardMove.ts and domain/task/listing.ts. listing.ts and application/pull-requests.ts use them; the dashboard imports them from the daemon as it does api/contract.ts (boardMove.ts keeps only the board's move rule, taskView.ts and MarkDoneDialog.vue drop their copies). Remove the "keep in step" comments that pointed at the copies. The SQL that mirrors a rule (DEPENDENCY_MET, claimNextTask) stays, and claimNextTask gets the same kind of agreement test DEPENDENCY_MET has in mark-done.test.ts.

  • pnpm check passes, including the app's vue-tsc.
  • pr_state === 'open' appears only in stage.ts under daemon/src and app/src (grep).
  • Test: for queued tasks across repo pause, dependency state and priority, the task claimNextTask picks is the first with no startWait.

Input rules in the domain

Each rule now inside a use case moves to the domain module of what it governs, returning an error message or null: domain/task/rules.ts (priority, turn and attempt limits, the model via isModel, "steps need a plan", no tasks on an archived repo), domain/repo/ (the network host format), domain/planner/proposals.ts (interval, max tasks, model), domain/notification.ts (event kinds, ntfy topic and server), and the slot count with Budget in domain/usage/. application/ keeps reading the input's shape (input.ts) and calls these.

  • pnpm check passes; every message a person sees is unchanged (the API and CLI tests pass unchanged).
  • Each rule module has pure tests of its limits and its message.
  • No numeric limit is written in application/tasks.ts, repos.ts or settings.ts (grep).

Not in this plan

  • Typed domain models (booleans, arrays and parsed JSON instead of row shapes; parsed timestamps), and a PullRequest value with the failure to open one kept as a task error rather than pr_state = 'failed': with the Drizzle plan's foundation step, which rebuilds the row-to-model mapping and db/types-check.ts.
  • A typed cause on a paused repo (doctor, setup, refused tool use), and Task.source as a union with a ticket source: before the Plane ticket-source work, which maps both.
  • Renaming API paths (/plan, /resolve).
