Task links and the dependency graph

Replace the single after_task with links: a task can depend on any number of others, and each link is one of two kinds. Builds on holds the task's start until the other is done and merged (today's --after). After lets it run at once and only holds its merge. Links refuse cycles, a stuck task makes everything that builds on it stuck with the root named, and the dashboard shows each task's dependencies and a graph of the whole queue. Written 2026-11-01. Stacked branches come later and only change how a builds-on link runs.

Why

With more than one slot, linked work is serialised more than it needs to be. A task can wait on only one other, and every link means "wait for the merge", even when the later task only has to land second and could run alongside. There is also no way to see a chain: the dashboard shows one "After #n" row and an "unblocks" chip, and nothing for a task that waits two links away on a task that failed.

The words

Added to CLAUDE.md's Domain language with this plan:

A link is one task depending on another, of one of two kinds. Builds on: B uses A's code, so B starts once A is done and merged, and B's branch includes A's work; if A is rejected, B is stuck. After: B only has to land after A, so B runs any time on its own branch from the base, and only its merge waits for A's. A task's links are its dependencies; the tasks linked to it are its dependents. Not a task's Needs, which are what a blocked worker asked for.

In code: LinkKind = 'builds_on' | 'after'. In the CLI: --builds-on and --after. In the UI: "Builds on #12" and "After #12", solid and dashed edges.

The rules

Builds on A After A
B may start when A is met: done and merged, done with no PR in a pr_mode off repo, or marked done by a person with no open PR (today's rule) at once
B may merge yes (A is merged by the time B starts) when A has landed or gone: met as on the left, or cancelled, its PR closed, or deleted. While A could still land (proposed, queued, running, blocked, failed, done with a PR not merged) B's merge waits, by hand and by auto-merge.
A rejected (cancelled, PR closed) B is stuck: it waits, and a person decides (retry A, unlink, or cancel B) B carries on; its merge is free
A failed or blocked B is stuck; a retry of A releases it B's merge waits, and the merge dialog says why
  • B starts when every builds-on link is met, and merges when every after link has landed or gone.
  • Stuck spreads down. B is stuck when a builds-on dependency is stuck itself, or is waiting on something stuck. The reason names the root: "waits on #10 (via #12), which failed". Only builds-on links carry it; an after link never stops a start.
  • No cycles, across both kinds: a cycle of after links would hold every merge in it forever. Linking refuses a link that would close one, and a task can't link to itself.
  • Links between repos are allowed, as after_task allows today; A's own repo's pr_mode decides "met".

Decisions

Decision Why
A task_links table; after_task is copied into it and no longer read Many links per task need a table. The column stays (shipped migrations aren't edited, and SQLite column drops need a rebuild) but nothing writes or reads it after the migration; db/tables.ts marks it so.
Today's --after becomes --builds-on; --after now means the looser kind The words should match the Domain language. You are the only user, so the flag flips in one go rather than through an alias. The delegate skill and cli/help.ts change with it. Old links copy over as builds on, so nothing already queued changes.
The kind is chosen when linking; builds on is the default in the dashboard's picker Only the person (or later the planner) knows whether B uses A's code. Mislabelling as after is the costly error (B runs without A's code), so the safe kind is the default.
The after gate is a merge problem, not a warning "B lands after A" should hold for a person's merge as well as auto-merge. It goes into mergeFindings as a new kind, so the merge dialog, agentdeck merge and auto-merge all read it. Unlinking is the way to merge anyway.
The graph is drawn by hand in SVG, no library A queue holds tens of tasks. A layered layout (columns by depth, order within a column by the average position of its dependencies) is about 100 lines in app/src/lib/, is unit-testable and adds no dependency. elkjs only if that proves messy.

1 · Links in the domain and the database

Domain (domain/task/link.ts, replacing dependency.ts):

  • LinkKind, Link { task_id, on, kind }.
  • linkState(link, dependency): for builds on, today's met / waiting / stuck; for after, landed-or-gone / holding.
  • startState(task, links, lookup): none, met, waiting on ids, or stuck with the root's reason, following builds-on links down (with a visited set).
  • mergeHold(links, lookup): the after links still holding the merge, each with a reason.
  • linkError(task, on, links): self link, already linked, or a cycle (reachability over both kinds).

Database: migration 18:

-- 18: task links (docs/plans/task-links.html). kind is builds_on | after. after_task is copied in and no longer read.
CREATE TABLE task_links (
  task_id INTEGER NOT NULL REFERENCES tasks(id),
  on_task INTEGER NOT NULL REFERENCES tasks(id),
  kind TEXT NOT NULL DEFAULT 'builds_on',
  created_at TEXT NOT NULL DEFAULT (datetime('now')),
  PRIMARY KEY (task_id, on_task)
);
CREATE INDEX task_links_on ON task_links(on_task);
INSERT INTO task_links (task_id, on_task, kind) SELECT id, after_task, 'builds_on' FROM tasks WHERE after_task IS NOT NULL;

Store (in Drizzle, after the port): linksOf(id), dependentsOf(id, kind?), addLink and removeLink, and the claim's "not waiting" condition over every builds-on link (NOT EXISTS an unmet one), still mirroring the domain's met rule. Repo deletion removes the repo's tasks' links. db/tables.ts, migrations.lock and the domain types follow, as for every migration.

  • Unit tests for every row of the rules table, stuck spreading two links down with the root named, and each cycle case.
  • An existing after_task becomes a builds-on link, and a task with two builds-on links is claimed only once both are met.
  • The SQL "not waiting" rule agrees with startState (the claim-agreement test covers links).
  • pnpm check and pnpm db:check pass.

2 · Linking, the CLI and API, the merge gate

  • Use cases (application/task/links.ts): linkTasks(db, id, { on, kind }) and unlinkTasks(db, id, on), refusing through linkError. addTask takes builds_on: number[] and after: number[]. waitingFor and unblocksOf work over links, and warnStuckDependents names every dependent that becomes stuck, transitively.
  • Merge gate: mergeFindings gets a lands_after kind, a problem ("lands after #12, which is still running"). Auto-merge maps it to wait. A merge that lands A asks for a PR re-read, so B's gate lifts on the next refresh.
  • CLI: agentdeck add … --builds-on 12,14 --after 9; agentdeck link 15 --builds-on 12 or --after 12; agentdeck unlink 15 12. show and ls print both kinds. cli/help.ts and the delegate skill (--after becomes --builds-on) change with it.
  • API: POST /api/tasks/:id/links with { on, kind }, DELETE /api/tasks/:id/links/:on. The task views carry links: { on, kind, state }[] and dependents: { id, kind }[], with waiting and unblocks kept for the queue chips. NewTask takes both lists. contract-check.ts covers the new use cases.
  • Adding, linking and unlinking work from the CLI and the API, and a cycle or self link is refused with a reason.
  • A task after another runs at once, and its PR can't merge (dialog, CLI, auto-merge) until the other lands or is gone.
  • A failed task notifies once for all the tasks it leaves stuck, two links down included.
  • pnpm check passes.

3 · Dependencies on the task page

A Dependencies card on the task's Overview, replacing the sidebar's After row: "Builds on" and "After" lists of the task's links, and "Waiting on this" for its dependents, each a row with the status icon, #id, title and its state (met, waiting, stuck: reason, holding the merge). Rows open the task. An Add link control takes a #id or title search and a kind (builds on by default), and each link has a remove button. The merge dialog's Unblocks line covers both kinds, and the queue chips read "waits on #12, #14".

  • A task's links and dependents show with their state, and links can be added and removed from the card.
  • A refused link (cycle, self) shows its reason in the card.
  • pnpm typecheck passes for the app.

4 · The graph view

A third queue mode next to list and board (QueueView.vue, the v shortcut cycles through all three):

  • Layout in app/src/lib/graph.ts (pure, unit-tested): the tasks that are linked or have dependents form the graph, unlinked tasks stay out. Layer by longest path from a root, order within a layer by the mean position of its dependencies, a few sweeps to cut crossings.
  • Drawing: SVG nodes as small cards (status icon, #id, title, repo), coloured by status; builds-on edges solid, after edges dashed; a stuck task and everything it holds outlined in the blocked colour. Click opens the task, hover highlights its chain up and down.
  • Filters: the queue's repo and search filters apply. Chains whose every task is done and merged hide unless "Show finished" is on.
  • Layout tests: a chain, a fan-out, a diamond and two separate graphs lay out without overlap.
  • The view shows a real queue's links with both edge styles, opens a task on click, and highlights a stuck subgraph.
  • pnpm typecheck passes for the app.

Settled

  • Links between repos stay allowed, as today, but get no work of their own: nothing needs them yet.
  • The graph shows chains only; tasks without links stay in the list and board.

Not in this plan

  • Stacked branches: a builds-on dependent starts from A's branch once A is done, with its PR on A's branch until A merges. It changes only how a builds-on link runs, and waits until the time between done and merged is measured.
  • The planner proposing links between its proposals, and approving a chain at once.
  • Priority flowing up to dependencies, "unblocks the most" as a claim tie-breaker, and cancel cascading to dependents.
  • Mapping Plane's blocked-by relations to builds-on links, with the ticket source.
