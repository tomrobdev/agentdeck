Move the db layer to Drizzle

Row types are written by hand in domain/ and cast onto query results, column lists are strings, and partial updates are built clause by clause, so a new column can silently miss a type or a query. Define the tables once with Drizzle on the existing node:sqlite connection, check the domain types against them at compile time, and port the stores one at a time behind the same Db methods, so nothing outside db/ changes. Written 2026-10-25; on 2026-11-01 the port was approved on 1.0.0-rc.5 instead of waiting for 1.0.

Where it starts

  • daemon/src/db/: about 760 lines, 72 prepared statements (27 in tasks.ts, 19 in repos.ts), eight stores merged into one Db in index.ts. Nothing outside db/ uses the connection directly.
  • Migrations: an append-only array in db/schema.ts, counted by PRAGMA user_version, all pending steps in one transaction. 17 steps have shipped.
  • Already in place as dev tooling: db/tables.ts defines every table, db/types-check.ts fails pnpm typecheck when a table and its domain type disagree, pnpm db:check fails when tables.ts and the migrations disagree, and drizzle.config.ts points Studio at the live database. drizzle-orm is a runtime dependency at exactly 1.0.0-rc.5; daemon/test/architecture.test.ts still allows it only in db/tables.ts.
  • Drizzle on npm, 2026-11-01: latest is 0.45.4, which has no node-sqlite driver. 1.0 has been a release candidate since 2026-04-30; rc.5 shipped 2026-10-21. The drizzle-orm/node-sqlite driver takes our DatabaseSync and has a synchronous API (.all(), .get(), .run()).

Decisions

Decision Why
Drizzle 1.0 with the node-sqlite driver, on the connection openDb already opens. Not better-sqlite3, and not an async ORM (Kysely, Prisma, TypeORM, MikroORM). No native module to break on a Homebrew Node upgrade. The stores are synchronous: atomically, claimNextTask and applyEvent read and write in one synchronous step, which an async query can't join. Drizzle and the remaining raw statements share one connection, so atomically covers both.
Pinned at exactly 1.0.0-rc.5, decided 2026-11-01. Moving to 1.0 is its own step (upgrade), once 1.0 is latest. 0.45 has no node-sqlite driver, and 1.0 has been a release candidate for six months. The spike passed every check on rc.5.
Only the core query builder: select, insert, update, delete and the sql template. Not the relational query API (orm.query.x.findMany({ with })). Keeps the move from rc.5 to 1.0 small: much of the work still landing in 1.0 is on the relational API.
Domain types stay the source of truth, in domain/. db/ asserts at compile time that each table's inferred row type equals its domain type. domain/ stays pure and import-free; a drifting column fails pnpm typecheck.
Keep the user_version migration runner. New steps are still appended SQL; the schema change is made in tables.ts first and pnpm db:generate prints the SQL to append. The runner is proven (crash test, one transaction) and the live database needs no baseline. Switching to drizzle-kit's own migrator would mean marking 17 shipped steps as applied in a database the daemon is using.
Keep atomically (savepoints on the shared connection). Don't use orm.transaction(). The spike showed a ROLLBACK TO undoes Drizzle's writes too, and existing callers nest inside it.
The Db methods keep their names and signatures. Each store is ported whole, tests unchanged. Column types stay as they are (flags as number, JSON as string) until step typed-columns. Application, API, CLI and dashboard code doesn't change, and each step is checked by the tests that already exist.
The guarded status change (applyEvent), the atomic claim (claimNextTask) and DEPENDENCY_MET may stay as sql templates where the builder would hide the guard. Those queries are the invariants. Readable SQL beats a clever builder chain there.

Findings, 2026-10-25

Branch spike/drizzle, commit 4c043be: drizzle-orm and drizzle-kit 1.0.0-rc.5 (exact), Node 26.12.0, SQLite 3.54.1. settings and repos ported; all 333 daemon tests pass with no test changed, and both typechecks pass. Question Answer
Sync API inside atomically Yes. .get(), .all() and .run() return synchronously and are typed that way; .run() gives { changes, lastInsertRowid }. A ROLLBACK TO on the shared connection undoes Drizzle's writes.
Inferred types vs Repo Match, with keys written in snake_case in tables.ts (no casing option needed) and text().$type<PrMode>() for unions. Select with getColumns(table), not by spreading the table. Drift found: repos.created_at exists in the table and not in Repo. Dropping a column from tables.ts fails tsc.
drizzle-kit under type stripping Works: generate loads tables.ts and its .ts imports from domain/ and writes correct SQL. pnpm holds back some of its install scripts ("pnpm approve"); nothing needed them.
pull, and a schema diff pull reads all 9 tables (it names fields in camelCase; rename to snake_case). Better as the drift check: drizzle-kit push --explain against a freshly migrated database, with the node:sqlite driver, reports "No changes detected" for the ported tables.

Migration steps that rebuild a table

Not queued with the port. Adding a foreign key or a CHECK in SQLite needs a table rebuild (create, copy, drop, rename), which drizzle-kit generates with PRAGMA foreign_keys=OFF around it. That pragma does nothing inside a transaction, and the runner runs every step in one. Add a step kind to db/schema.ts that runs on its own, outside the transaction, with foreign keys off, then runs PRAGMA foreign_key_check and fails the migration if it reports anything. Needed before adding the missing foreign keys (task_events, task_plans, notifications, tasks.after_task), which are their own plan.

  • A test rebuilds a table with child rows through the new step kind, and the rows and their references survive.
  • A rebuild that leaves a broken reference fails the migration and leaves user_version unchanged.
  • pnpm check passes.

Typed columns

Not queued with the port. Flags become integer({ mode: 'boolean' }) (auto_approve, auto_resolve, sandbox, auto_merge) and JSON text becomes text({ mode: 'json' }).$type<…>() (network, allowed_tools, auto_merge_skip, plan_steps, needs). The stored values don't change, so no migration. The domain types change with them, and so do the use cases, api/contract.ts and the dashboard. One group of columns per task.

  • No JSON.parse or JSON.stringify of these columns left outside db/.
