Move the db layer to Drizzle

Row types are written by hand in domain/ and cast onto query results, column lists are strings, and partial updates are built clause by clause, so a new column can silently miss a type or a query. Define the tables once with Drizzle on the existing node:sqlite connection, check the domain types against them at compile time, and port the stores one at a time behind the same Db methods, so nothing outside db/ changes. Written 2026-10-25.

Where it starts

  • daemon/src/db/: about 780 lines, 55 prepared statements, eight stores merged into one Db in index.ts. Nothing outside db/ uses the connection directly. 13 test files open a database.
  • Migrations: an append-only array in db/schema.ts, counted by PRAGMA user_version, all pending steps in one transaction. 11 steps have shipped.
  • Drizzle on npm, 2026-10-25: latest is 0.45.4, 1.0 is at rc.5. The drizzle-orm/node-sqlite driver takes our DatabaseSync and has a synchronous API (.all(), .get(), .run()).

Decisions

Decision Why
Drizzle 1.0 with the node-sqlite driver, on the connection openDb already opens. Not better-sqlite3. No native module to break on a Homebrew Node upgrade, and no second migration from 0.45 to 1.0. Drizzle and the remaining raw statements share one connection, so atomically covers both.
Gated on 1.0 reaching latest. Until then only the spike (step spike) runs, on a throwaway branch. Going earlier means pinning an exact rc and changing the CLAUDE.md rule on purpose. rc.1 changed the casing API; breaking changes are still landing. CLAUDE.md defers Drizzle until 1.0 is stable.
Domain types stay the source of truth, in domain/. db/ asserts at compile time that each table's inferred row type equals its domain type. domain/ stays pure and import-free; a drifting column fails pnpm typecheck.
Keep the user_version migration runner. New steps are still appended SQL; drizzle-kit only writes the SQL for a step from the schema change, and a test checks the migrated database matches the Drizzle schema. The runner is proven (crash test, one transaction) and the live database needs no baseline. Switching to drizzle-kit's own migrator would mean marking 11 shipped steps as applied in a database the daemon is using.
The Db methods keep their names and signatures. Each store is ported whole, tests unchanged, one store per task. Application, API and CLI code doesn't change, and each step is checked by the tests that already exist.
The guarded status change (applyEvent), the atomic claim (claimNextTask) and DEPENDENCY_MET may stay as sql templates where the builder would hide the guard. Those queries are the invariants. Readable SQL beats a clever builder chain there.

Spike: one store on the rc

On a throwaway branch (spike/drizzle), pin drizzle-orm and drizzle-kit to the current rc and port settings and repos. Not merged.

Findings, 2026-10-25

Branch spike/drizzle, commit 4c043be: drizzle-orm and drizzle-kit 1.0.0-rc.5 (exact), Node 26.12.0, SQLite 3.54.1. settings and repos ported; all 333 daemon tests pass with no test changed, and both typechecks pass.

Question Answer
Sync API inside atomically Yes. .get(), .all() and .run() return synchronously and are typed that way; .run() gives { changes, lastInsertRowid }. A ROLLBACK TO on the shared connection undoes Drizzle's writes.
Inferred types vs Repo Match, with keys written in snake_case in tables.ts (no casing option needed) and text().$type<PrMode>() for unions. Select with getColumns(table), not by spreading the table. Drift found: repos.created_at exists in the table and not in Repo. Dropping a column from tables.ts fails tsc.
drizzle-kit under type stripping Works: generate loads tables.ts and its .ts imports from domain/ and writes correct SQL. pnpm holds back some of its install scripts ("pnpm approve"); nothing needed them.
pull, and a schema diff pull reads all 9 tables (it names fields in camelCase; rename to snake_case). Better as the drift check: drizzle-kit push --explain against a freshly migrated database, with the node:sqlite driver, reports "No changes detected" for the ported tables.
Cost Per call, Drizzle against the raw store: getSetting 3.6 vs 2.7 µs, budget() 19.7 vs 9.1 µs, listRepos 16.4 vs 17.8 µs, getRepo 12.9 vs 11.2 µs. Microseconds against a 5-second tick: no concern.

Verdict: go, still gated on 1.0 reaching latest. Changes to this plan: the foundation step adds created_at (and any other drift the type checks find) to the domain types, and uses push --explain as its schema check; the tasks step's cost check becomes an absolute limit.

Foundation: the tables, and checks against drift

Add drizzle-orm (runtime) and drizzle-kit (dev), exact versions. db/tables.ts defines every table to match the migrated schema exactly (start from drizzle-kit pull). openDb also builds drizzle({ client }) on the same connection and hands it to the stores. db/types-check.ts asserts each table's select type equals its domain type (Task, Repo, Run, …). Fix the drift the assertions find (the spike found repos.created_at missing from Repo). A pnpm db:check script migrates a fresh scratch database and runs drizzle-kit push --explain against it, failing unless it reports no changes; pnpm check runs it. drizzle.config.ts and a pnpm db:generate script that prints the SQL for a schema change. No store changes yet.

  • pnpm check passes, including the crash test.
  • Removing a column from a domain type, or from tables.ts, fails pnpm typecheck or pnpm test.
  • pnpm db:generate on the unchanged schema produces no SQL.

Rules and docs

CLAUDE.md: "SQL lives only in db/" becomes "queries live only in db/, through Drizzle; raw sql only where the builder hides a guard"; the Drizzle line in Rules is replaced by how to add a column (change tables.ts and the domain type, run pnpm db:generate, append its SQL as a new step). Remove raw from Db if nothing in db/ needs it outside openDb.

  • CLAUDE.md describes the new way of adding a column, step by step.
  • pnpm check passes.

Not in this plan

  • drizzle-kit's own migrator and migration table (see Decisions).
  • Generating app/src/api.ts from the daemon's types. The dashboard keeps its mirrored copy.
  • Cascading foreign keys (SQLite needs a table rebuild to add them).
  • Drizzle Studio, or any change to how the live database is inspected.
