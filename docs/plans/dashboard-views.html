Dashboard views: Linear-style queue, GitHub-style task page

A plan for the AgentDeck dashboard's next step: a dense, keyboard-driven task list and board modelled on Linear, and a task page modelled on a GitHub pull request, with a diff viewer, a file tree and a code viewer that later work (snippets, documents) builds on. Why and scope

Reviewing what an agent did is the slowest part of using AgentDeck. Today the dashboard shows a task's status, its prompt, the final message as plain text and a streamed log. To see the code, you open the worktree in an editor or wait for the PR on GitHub. The pilot's goal is tasks that become green draft PRs with nobody stepping in, and a fast way to check that work, inside the dashboard, is what makes that trust possible.

The queue view has a different problem: as the queue grows, a flat list with tabs stops telling you what needs you. Linear's list solves this with status groups, dense rows, a display menu and the keyboard.

In scope: the dashboard (app/), read-only git endpoints in the daemon, a task event history, and structured file paths in the log. Out of scope: editing code from the dashboard, comments, labels and multi-user features.

Wording: the UI keeps the domain words from CLAUDE.md. A row is a task, never an issue or ticket; an attempt is a run.

Decisions

The four open questions from the first draft, settled so building can start. Each can be revisited, and each notes what changing it would cost.

D1 · New dependencies: markdown-it, DOMPurify, highlight.js

Markdown is needed in three places (prompts, final messages, .md files) and code highlighting in two (diffs, the file viewer). Writing either ourselves is a poor trade.

  • markdown-it (about 100 KB): CommonMark, with raw HTML off.
  • DOMPurify (about 20 KB): sanitises its output anyway, since agent-written markdown is untrusted.
  • highlight.js, core plus about 20 registered languages: synchronous, small, and good enough for review. Shiki is more accurate but larger and asynchronous (WASM or a regex engine). It can replace highlight.js later behind the same highlight(code, lang) function.

The daemon gets no new dependencies. Diffs are parsed by our own small parser, because unified diff is a simple format.

D2 · Navigation: hash routes, list full width, task page full width

Routes are #/ (queue, list or board) and #/tasks/16/<tab> (task page). Clicking a row opens the page, and Esc or Back returns to the queue with its scroll and selection kept, as in Linear. Diffs and code need the full width, which the old split pane never had. A peek panel (Space) is left for later. Hash routing is about 30 lines, so there's no router dependency.

D3 · Priority: keep the integer, show four levels

Priority stays an unbounded integer: the scheduler orders by it, and the planner and CLI set it. The UI shows Linear-style bars by bucket, with the number in the tooltip and the sidebar.

Value Shown as
0 No priority (dashes)
1–19 Low (1 bar)
20–39 Medium (2 bars)
40–59 High (3 bars)
60+ Urgent (filled square)

D4 · Short id: keep #16

Ids are global, and branches (agentdeck/task-16), the CLI and notifications all use #16. A per-repo key such as AD-16 would need a mapping everywhere for little gain. Rows show #16 in the id column where Linear shows its key.

Architecture

Dashboard (app/src)

  • router.ts: hash routes as a reactive route, plus go()
  • taskView.ts: groups, states, sorts and priority levels, moved out of TaskList.vue. It mirrors daemon/src/domain/task/listing.ts
  • render.ts: markdown() and highlight(), the only place the new dependencies are imported
  • components/queue/: QueueView, ListView, BoardView, FilterBar, DisplayMenu, StatusIcon, PriorityIcon
  • components/task/: TaskPage, OverviewTab, RunsTab, ChangesTab, CodeTab, Sidebar
  • components/files/: FileTree, DiffView, CodeView, Markdown. These are standalone so snippets and documents can reuse them

Daemon (daemon/src)

  • db/schema.ts: migration step 6, the task_events table
  • db/tasks.ts: applyEvent, claimNextTask and addTask record events. eventsForTask() reads them
  • adapters/git.ts: changedFiles, filePatch, listTree, readFile, commitsBetween. These read git objects, never the worktree
  • domain/files/: path validation, size limits and numstat parsing (pure)
  • application/files.ts: resolves a task to its repo path, head and base, then calls git
  • api/server.ts: four GET routes. Task detail gains events
  • domain/run/log.ts: tool entries gain a file field

Layering stays as CLAUDE.md sets it: the git adapter knows nothing of tasks, the application layer joins db and git, and the domain stays pure. Endpoints read from git objects (git show <sha>:<path>), not the filesystem. That has three effects:

  • They work after agentdeck clean removes the worktree, because the branch is kept.
  • A path can't reach outside the repo.
  • A running agent's half-written files are never shown as committed.

API contract

The contract both sides build against. Each ref is one of two words, never a ref name the client supplies:

  • head: the task's branch
  • base: the merge base of that branch with the repo's base branch (or origin/<base> when only that exists)

A task with no branch yet answers 400 {"error": "task has no branch yet"}.

GET /api/tasks/:id            (existing) + events: TaskEventRow[]
  TaskEventRow = { id, task_id, type, from_status, to_status, reason, at }
  type: created | claim | finish | rate_limited | cancel | approve | reject | retry | recover

GET /api/tasks/:id/changes
  → { base_ref: "main", base: sha, head: sha,
      files: [{ path, old_path: string|null, status: "A"|"M"|"D"|"R", additions, deletions, binary }],
      commits: [{ sha, subject, author, at }] }

GET /api/tasks/:id/diff?path=p
  → { path, patch: string, truncated: boolean }          patch capped at 256 KB

GET /api/tasks/:id/tree?ref=head|base&path=dir           one level, folders first
  → { ref, sha, path, entries: [{ name, path, type: "file"|"dir", size: number|null }] }

GET /api/tasks/:id/file?ref=head|base&path=p
  → { path, ref, sha, size, binary, truncated, text: string|null }   text capped at 512 KB

LogEntry tool  → { kind: "tool", name, input, file?: string }   file_path / path / notebook_path

Paths are repo-relative. An absolute path, a .. segment, a NUL byte, or a path starting with - is a 400. Git runs with -- before paths. All git calls run in the repo's main checkout, which shares refs with the worktrees.

Phase 1 · Linear-style list

dashboard onlybuilds on task-list-filters

Why

The tabs hide what matters. You see either the active tasks or the ones that need you, never both, and counts are the only summary. Linear shows every group at once, collapsible, with dense rows you can scan and act on from the keyboard.

Design

[ ≡ List | ▦ Board ]   Status is Blocked, Stuck ×   Repo is demo ×   + Filter      ⌕ search   Display ▾
▾ Needs you  3
  ◔  ▮▮▮  #16  Run workers in the Claude Code sandbox     AgentDeck  ⎇ draft  waiting #15   2h
▾ Proposed  2
  ◌  ▮▯▯  #4   Add escapeHtml(s) helper with tests         demo       planner             3h
▾ Running  1
  ◐  ▮▮▯  #9   Cheap queue checks in the scheduler tick    AgentDeck                      5m
▸ Done  11
  • Groups, in attention order: Needs you (blocked, failed, stuck), Proposed, Running, Queued (including waiting), Done, Cancelled. Headers collapse, show counts, and are remembered. Cancelled starts collapsed.
  • Group by status (the default), repo, priority level, or nothing. Order within a group uses the existing sorts.
  • Rows are one 34 px line:
    • a status icon: each status has its own shape and colour, so it's not colour-only
    • a priority icon
    • the id, the title, then property chips (repo, PR state, planner, waiting/stuck, attempt)
    • the time, aligned right
    • a blocked reason as a second muted line, so a failure is visible without opening the task
  • Display menu: group by, order by, which properties to show, and whether to show empty groups. It replaces the tabs and the sort dropdown.
  • Filter bar: each active filter is a removable chip (Status is …, Repo is …, Source is planner). "+ Filter" opens a small menu. The search stays.
  • Keyboard:
    • j/k or arrows move the selection, Enter opens, / goes to search
    • a approves a proposal, r retries
    • v toggles list and board, c opens New task
    Cancel stays a button, because stopping a run loses work.
  • Hover actions at the row end: Approve, Retry, Open PR.

Files

QueueView.vue, ListView.vue, FilterBar.vue, DisplayMenu.vue, StatusIcon.vue, PriorityIcon.vue, taskView.ts. TaskList.vue is removed.

Done when

  • Every group shows at once, with counts. Collapsing one is remembered across reloads.
  • Grouping by repo and by priority works, and each group keeps the chosen order.
  • The whole list can be worked from the keyboard, and a selected row stays in view.
  • The status icons can be told apart in greyscale.
  • The 2-second poll doesn't move the selection or the scroll position.

Phase 2 · Board

dashboard onlyafter phase 1

Why

A board shows flow: how much is waiting for you compared with running and done. It also makes approving or retrying a batch quick. With a few dozen tasks it's the least urgent phase, but it reuses phase 1's groups and filters, so it's cheap.

Design

  • Columns: the same groups as the list's status grouping, each with a header count. Cards are a compact row: id, priority, title on up to 2 lines, chips. Filters and search apply as in the list.
  • Dragging a card maps only to real lifecycle events, and drop targets light up only where the move is allowed:
    From To Event
    Proposed Queued approve
    Proposed Cancelled reject
    Needs you (blocked, failed), Done, Cancelled Queued retry
    Queued, Needs you Cancelled cancel
    A running task can't be dragged. Stopping it is a deliberate button press on the task page. The daemon still guards every move (applyEvent), so a stale board can't do harm: a refused move shows a toast.
  • Reordering within a column to change priority is left for later.

Done when

  • Each allowed drop calls the matching endpoint, and the card moves on the next poll.
  • Moves that aren't allowed show no drop target.
  • Columns scroll on their own, and the board scrolls sideways on a narrow window.

Phase 3 · GitHub-style task page

daemon: migration step 6dashboardadds markdown-it, DOMPurify

Why

A task is a pull request in all but name: a description (the prompt), a branch, attempts that act like CI runs, and a final message that acts like the author's summary. The PR page layout is one reviewers already read fluently. The timeline also answers "what happened to this task?", and today nothing does.

Design

← Queue   Run workers in the Claude Code sandbox  #16
          ● queued   agentdeck/task-16 → main   2 runs   created by planner 2h ago     [Retry] [Cancel]
          Overview · Runs 2 · Files changed 11 · Code
┌──────────────────────────────────────────────┐ ┌──────────────────┐
│ Prompt  (rendered markdown, collapsible)     │ │ Status   queued  │
│ ─ timeline ───────────────────────────────── │ │ Priority ▮▮▮ 37  │
│ ○ created by the planner              2h     │ │ Repo  AgentDeck  │
│ ✓ approved                            2h     │ │ Model    opus ✎  │
│ ▶ run 1 started                       1h     │ │ Attempts  1 / 2  │
│ ✗ run 1 failed · tests ✗ · 66 turns   48m    │ │ Turns   max 80 ✎ │
│   ▸ final message (markdown)                 │ │ After  #15 ✓     │
│ ↻ retried                             45m    │ │ PR  draft ↗      │
└──────────────────────────────────────────────┘ │ Branch  copy     │
                                                 │ Worktree copy    │
                                                 └──────────────────┘
  • Header: the title (click to edit while the task is editable), #id, a status pill, branch → base, the run count, and actions (Approve or Reject, Retry, Stop or Cancel).
  • Overview: the prompt rendered as markdown, then a timeline that merges task_events, runs (start, end, tests, turns, tokens) and the PR (opened, merged). Each run ends with its final message, rendered, and folded unless it's the latest run and didn't finish done. Older tasks have no events, so their timeline is built from created_at and runs.
  • Runs tab (the checks view): one card per run, showing outcome, duration, turns, tokens, refused tools, and setup and test results with their output. The live log is embedded for the selected run. This is today's TaskDetail bottom half, rearranged.
  • Sidebar: properties. Priority, model and max turns are edited inline through the existing POST /api/tasks/:id, only for editable statuses. Branch and worktree have copy buttons. The PR link opens in the browser.
  • Links in rendered markdown open in the system browser (Tauri opener), never inside the webview.

Daemon

-- migration step 6
CREATE TABLE task_events (
  id INTEGER PRIMARY KEY,
  task_id INTEGER NOT NULL,
  type TEXT NOT NULL,           -- created | the TaskEvent type
  from_status TEXT, to_status TEXT,
  reason TEXT,
  at TEXT NOT NULL DEFAULT (datetime('now'))
);
CREATE INDEX task_events_task ON task_events(task_id, id);

Events are written in the same statement batch as the status change: inside applyEvent after a successful guarded UPDATE … RETURNING, in claimNextTask, and in addTask (created). A refused event writes nothing. Each event row and its status change are written in one transaction, so a crash can't leave one without the other.

Done when

  • Every status change after migrating shows in the timeline, in order, with its reason.
  • Prompts and final messages render as markdown. A <script> or onerror in agent output does nothing.
  • The Back button and Esc return to the queue with its scroll position kept.
  • The tests cover event recording for each event type, and that a refused transition records nothing.

Phase 4 · Files changed

daemon: git read endpointsdashboardadds highlight.js

Why

This is the review itself. Today the only way to see what an agent changed is the worktree in an editor or the PR on GitHub, and PRs only exist for repos with pr_mode on. A diff inside the dashboard means a proposal, a blocked run or a done task can be judged where it's listed.

  • File tree of changed paths, with folders compressed (daemon/src), +/− counts and A/M/D/R badges. Clicking a file scrolls to it.
  • Diffs: files load their patch as they scroll into view, so 50 files don't mean 50 requests at once. Each file folds and has a "Viewed" box, stored per task and file in local storage, which also folds it. Patches over the limit show "Diff too large", and binary files show "Binary file".
  • Unified or split view, with syntax highlighting by file extension, applied per line so a diff's partial lines still highlight.
  • Markdown files get a rendered preview toggle, so an ADR can be read as a document.
  • Commits menu: the commits on the branch, newest first. Picking one is left for later. For now it's information: a retry continues on the same branch, so you can see which commits came from which run.

Daemon

New git adapter functions:

  • changedFiles(repoPath, base, head): git diff --numstat -z -M plus --name-status
  • filePatch(repoPath, base, head, path)
  • commitsBetween(repoPath, base, head)

application/files.ts resolves the task's repo, head (rev-parse <branch>) and base (merge-base with startPoint). Parsing numstat, validating paths and the size limits live in domain/files/ and are unit-tested. The end-to-end test makes a branch with an added, a modified, a deleted, a renamed and a binary file, and checks the endpoints.

Done when

  • The diff for task-16 matches git diff main...agentdeck/task-16: same files and line counts.
  • Renamed, deleted and binary files show correctly, and oversized patches are cut off with a notice.
  • Paths with .., absolute paths and option-like paths are refused, with tests.
  • The Viewed boxes survive a reload.

Phase 5 · Code browser and file viewer

daemon: tree and file endpointsdashboard

Why

A diff shows what changed, not the code around it. To judge a change you often need the whole file, a neighbouring module, or the document the agent wrote. This is also the base for what comes next: the user wants task pages to show code snippets and documents, and both need a tree, a file viewer and line links.

Design

  • Ref switch: head (the task branch) or base. Changed files are marked in the tree with a dot.
  • Tree: loads one level at a time, folders first, with a quick filter box. t opens a fuzzy file finder across the paths loaded so far and the changed files. Breadcrumbs sit above the file.
  • File viewer:
    • line numbers and syntax highlighting
    • click a line number to select it, shift-click for a range, and the URL becomes #/tasks/16/code?path=…&L=10-20
    • Copy, and Copy path
    • Markdown files show rendered by default, with a Raw toggle
    • Images (png, jpg, gif, svg as text) show a placeholder for now, because the CSP allows only data: URIs
    • binary and oversized files show a notice
  • Open in editor: copies the absolute path in the worktree, if it still exists. Real "open" support through Tauri is left for later.

Reusable pieces

FileTree takes a loader function, so the same tree serves "changed files" (all paths up front) and "repo tree" (loaded lazily). CodeView takes text, a language and an optional line range. Markdown takes text. Phase 6 and later work embed these with nothing else attached.

Done when

  • The AgentDeck repo browses to any file at head or base, and a 3,000-line file scrolls smoothly.
  • A line link, reopened, scrolls to and highlights those lines.
  • The tree works after agentdeck clean has removed the worktree.

Phase 6 · Snippets and documents in context

daemon: log parserdashboard

Why

The log and the final message keep naming files: "Read daemon/src/worker.ts", "I wrote docs/adr/0001-worker-sandbox.md". Each mention should be one click from the code. Documents the agent wrote, such as ADRs and plans, are often the most important output and belong on the Overview tab.

Design

  • Log parser: tool entries carry a file field taken from file_path, path or notebook_path, so a long input can no longer cut the path off. The UI strips the worktree prefix and links the entry to Code at head.
  • Final messages and prompts: inline code that looks like a repo path (contains a / and a known extension, and is in the changed files or the tree) becomes a link.
  • Documents card on Overview: changed .md files under docs/, or at the repo root, are listed. The first one is expanded, using Markdown.
  • Snippet hover: hovering a path:line link shows ±5 lines in a popover, using CodeView with a line range.

Done when

  • Task #16's log entries for Read and Edit link to the right files.
  • Its ADR shows as a document on Overview.
  • Paths that don't exist aren't turned into links.

Not in this plan

  • A peek panel (Space), a command palette (⌘K), and setting priority by dragging within a board column.
  • Diffs for each run. This needs runs.head_sha recorded at the end of each run, as a new migration step.
  • Comments on diff lines that feed into a retry prompt. This is the natural next step after review, and its own plan.
  • Moving search to the server for queues beyond the 200 most recent closed tasks.
  • Swapping highlight.js for Shiki if its accuracy matters.

Build order

The daemon work (step 6 events, the git endpoints, the log file field) and the dashboard's phases 1 and 2 don't depend on each other, so they're built in parallel. Then phase 3 (the page shell and timeline), then 4, 5 and 6, each committed separately on branch dashboard-views with tests and the typecheck passing.
