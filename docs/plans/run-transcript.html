A run's log as a transcript

The task page's Runs tab shows what claude did but never what came back, and each tool call is a cut line of raw JSON. Make the log read like Claude Code's own transcript: each tool call in a few words with its output folded beneath it, claude's text as markdown, and runs of file reads folded into one line.

Why

  • parseLogLine (daemon/src/domain/run/log.ts) ignores user events, which carry every tool result. A failing pnpm test shows as a Bash call and nothing else.
  • A tool entry's input is the call's JSON cut at 400 characters, so an Edit shows a slice of old_string, not what changed.
  • app/src/components/task/LogView.vue shows claude's text as plain wrapped text, though Markdown.vue exists and the run's final message already uses it.
  • The log's events carry a timestamp, an id on each tool_use and a tool_use_id on each tool_result, and a parent_tool_use_id on a subagent's events. None of it reaches the view.
  • toolText in daemon/src/domain/run/live.ts already words a tool call for the live line ("Edit worker.ts").

Log entries that carry results and a summary

Change the daemon's log entries (LogEntry in daemon/src/domain/run/log.ts, pure):

  • A tool entry gains id (the tool_use id) and summary: the call in a line, by tool. Bash: the command. Read, Write, Edit, NotebookEdit: the file. Grep: the pattern and where. Glob: the pattern. WebFetch: the URL. Task or Agent: its description. TodoWrite: "n todos, k done". Anything else: the first string field. Keep input and file as they are.
  • An Edit, MultiEdit or Write entry gains change: the lines added and removed, and the old and new text, each cut at 2 KB, so the view can show a small diff.
  • A new tool_result entry for each tool_result block in a user event: { kind: 'tool_result', id, ok, output, lines }. ok is false when is_error is set. The content may be a string or a list of blocks: join the text blocks, and write [image] for an image. output is the first 4 KB; lines counts the whole output's lines.
  • Every entry from a claude event gains at, the event's timestamp, when it has one, and parent, its parent_tool_use_id, when it comes from a subagent.
  • Word the summary in one function beside parseLogLine, and have toolText in daemon/src/domain/run/live.ts use it, so the live line and the log say the same thing.
  • Update LogEntry in daemon/src/api/contract.ts to match (daemon/src/api/contract-check.ts fails until it does).
  • The CLI's log (printLog in daemon/src/cli/format.ts) prints each tool's summary instead of its JSON, and under a failed result its first three lines.
  • daemon/test/run-log.test.ts covers: a result with string content and one with text blocks and an image; an error result; output cut at 4 KB with lines still counting all of it; the summary for each tool named above and for an unknown one; change on an Edit; at and parent taken from the event.
  • The existing tests in daemon/test/run-log.test.ts and daemon/test/live.test.ts still pass.
  • pnpm check passes.

The transcript view

Rewrite app/src/components/task/LogView.vue as a transcript. Put the grouping (pairing each result with its call, folding, nesting) in a pure helper, app/src/lib/transcript.ts, so the component only draws it.

  • A tool call is one line: a marker, the tool's name, then its summary. The file in it stays a link that opens the file, as now. While the run is live, a call with no result yet shows a small spinner.
  • Its result sits beneath it: the first line, then "▸ n lines" that unfolds the rest. A result that failed is in the failed colour and starts unfolded.
  • An Edit or Write shows +n −n and unfolds to a small diff.
  • Claude's text renders with Markdown.vue, with isPath as RunsTab.vue passes it to the final message.
  • Back-to-back Read, Grep, Glob and LS calls fold into one line, "Explored n files", which unfolds to the calls. A subagent's entries (parent) fold under their Task or Agent call.
  • Each entry shows the time since the run's first entry, from at, in a narrow muted gutter.
  • While the log streams and the reader has scrolled up, a "Jump to live" button scrolls back down and sticks there again.
  • Setup and test output keep their fold. Turn their terminal colour codes into colour (bold and the eight basic colours) with a small helper in app/src/lib/, no new dependency; drop any other codes.
  • A log written before this change (no id, no results) still shows, one line per call.
  • In the dashboard against a live daemon, a running task's Runs tab shows each tool call in a line with its output folded beneath. A failing Bash call shows in red with its output open.
  • A run of reads shows as "Explored n files"; claude's text shows as markdown, with code and lists rendered.
  • Scrolling up during a live run shows "Jump to live", and clicking it follows the log again.
  • An old run's log, from before the change, still shows.
  • pnpm check passes.

Out of scope

  • A terminal emulator (xterm.js and the like): the log is structured events, not a terminal's output.
  • Claude's thinking blocks.
  • Searching or filtering the log.
  • How the run log is written (daemon/src/adapters/run-log.ts) or streamed (daemon/src/api/log-stream.ts).
