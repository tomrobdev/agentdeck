Checked rules and generated diagrams

CLAUDE.md states rules, and architecture.test.ts checks most of them, but some are only stated, docs name files that have moved, and "green" is defined three times (pnpm check, CI, the repo's test_cmd) in three different ways. Make every rule either checked or visibly unchecked, define green once, and add a docs/architecture.md whose diagrams are generated from the code and fail pnpm test when they go stale. Written 2026-11-01.

Where it starts

  • daemon/test/architecture.test.ts parses every file in daemon/src with the TypeScript compiler and checks 11 rules: layers, actions.ts as the only way into application/, contract.ts imports nothing, packages, cycles, a pure domain/, SQL only in db/, guarded status changes, claude in its own process group, and unchanged migration steps. app/src is not checked.
  • Not checked: "application code keeps no module-level state other than a lock", "keep this checkout on main", the dashboard layout, and the domain language.
  • Green today: pnpm check runs format, typecheck, db:check, tests and the crash test (10). CI (.github/workflows/check.yml) runs format, typecheck, tests and the crash test (5), but not db:check. The AgentDeck repo's test_cmd is a hand-written chain of four commands.
  • On 2026-11-01 reload_on_change restarted the live daemon onto an uncommitted migration step (17), which then ran on ~/.agentdeck/agentdeck.db. Had the step changed before it was committed, the live database would have kept the old version without anyone noticing.
  • The delegate skill named daemon/src/domain/planner/plan.ts, which no longer exists. Fixed by hand before this plan was queued (workers can't edit .claude/).

Decisions

Decision Why
Every new check is a test in pnpm test, not a separate script. pnpm test runs in CI, in AgentDeck's test_cmd and before an auto-merge, so a check there gates all three with no extra wiring.
Diagrams are Mermaid, in generated blocks between markers in hand-written markdown. GitHub, VS Code and PR diffs render Mermaid; generating it is string building, so no new dependency. Markers let the prose stay hand-written while the blocks are replaced whole.
What can't be generated (the system context, one task's run) is written by hand and checked for the names it uses. A renamed function or a new adapter fails the test, which is how hand-drawn diagrams usually go stale.
The reload guard covers only migration steps and the branch. Other uncommitted daemon code still reloads, as reload_on_change intends. Code can be reloaded again; a migration step that ran on the live database can't be taken back, and a branch other than main swaps the live daemon's code.
Each CLAUDE.md rule gets an id; each check names the id it enforces; rules with no check are listed as unchecked, with why. Adding a rule then forces the question "how is this enforced?", and the answer is visible in one place.

Don't reload onto an uncommitted migration step

reloadDecision (domain/daemon/restart.ts) takes one more input, blocked: string | null: why the code on disk must not be loaded. When it is set and the restart wasn't requested, the decision is { pending: false, exit: false } with the reason, so the daemon keeps running and claiming on its current code. The git adapter gets two reads: whether daemon/src/db/schema.ts differs from HEAD, and the checked-out branch. src/daemon.ts works out blocked when a change arrives: "db/schema.ts has uncommitted changes" or "the checkout is on <branch>, not main". It logs the reason once per distinct reason, not every tick. A requested restart (the dashboard's button, agentdeck restart) is unchanged.

  • Unit tests on reloadDecision: blocked and idle doesn't exit and isn't pending; blocked and requested exits.
  • A test with a temporary git repo: an uncommitted change to db/schema.ts blocks; committing it clears the block.
  • pnpm check passes.

Define green once

Root package.json: check:fast runs format check, typecheck, db:check and test; check runs check:fast then the crash test, with its iteration count from CRASH_ITERATIONS (default 10). .github/workflows/check.yml runs pnpm check with CRASH_ITERATIONS=5 in place of its separate steps. Update the README's command list. After merging, a person sets the repo's test command: agentdeck repo set AgentDeck test_cmd "pnpm check:fast".

  • CI's only check step is pnpm check, and it passes on the PR.
  • pnpm check:fast fails when db/tables.ts drifts from the migrations.

Paths named in docs exist

A test reads CLAUDE.md, README.md, every .claude/skills/*/SKILL.md, docs/*.md and docs/adr/*.md, finds every backticked file path (a name with a file extension; skip ones with *, <, ~ or a $), and fails for each one that exists under none of: the repo root, daemon/, daemon/src/ and its layer folders, app/, app/src/, docs/. A path written relative to a folder named just before it (planner/ (proposals.ts)) is resolved against every folder in the tree with that name. Plans in docs/plans/ are left out: they describe files that don't exist yet.

  • The test passes on the current docs, and fails, naming file and line, when a named path is renamed.
  • pnpm check passes.

docs/architecture.md, generated and checked

daemon/scripts/docs.ts (pnpm docs, root and daemon) rewrites the blocks between <!-- generated:NAME --> and <!-- /generated --> in docs/architecture.md, leaving everything else alone. Output is deterministic: sorted, no timestamps. Generated blocks:

  • layers: Mermaid flowchart of daemon/src's layers with the number of imports on each edge.
  • data-model: Mermaid erDiagram from db/tables.ts (Drizzle's getTableConfig). Real foreign keys are solid lines; *_id and after_task columns without one are dotted, so missing keys show. Every column, with its type and whether it's nullable.
  • lifecycle: Mermaid stateDiagram-v2 from RULES in domain/task/lifecycle.ts, one edge per status pair with its events. An edge that every run-ending event takes (the one out of cancel_requested) is labelled "any run end".
  • routes: a table of method, path and the use case each route in api/routes/ calls.
  • settings: a table of every setting, its default and its meaning, from the domain's defaults.
  • migrations: a table of migration steps, numbered, with the comment above each.

Two hand-written sections: system context (dashboard, CLI, daemon, claude, git, gh, launchd, notifications, SQLite) as a flowchart, and one task's run (tick, governor, claim, sync, claude, tests, PR, auto-merge, pr_merged) as a sequenceDiagram. A test fails when the docs are stale, saying to run pnpm docs; when an adapters/*.ts file isn't named in the system context; and when a backticked identifier in either hand-written section isn't exported from daemon/src.

  • pnpm docs run twice in a row changes nothing the second time.
  • Adding a lifecycle rule, a column or a route without running pnpm docs fails pnpm test.
  • Every diagram renders on GitHub (check the PR's rich diff).
  • pnpm check passes.

Each rule names its checks

Give each rule in CLAUDE.md's Boundaries and Rules sections an id, as <!-- rule:ID --> at the end of its line. Prefix each check's test name with the ids it enforces: test('[sql-in-db] SQL runs only in db/', …). A test reads CLAUDE.md and the test files and fails when a test names an id CLAUDE.md doesn't have, or when a rule has no test and isn't in the test's UNCHECKED list, which gives the reason for each. pnpm rules prints rule, its tests, or "unchecked: reason". CLAUDE.md gets two lines: point at docs/architecture.md as the map of the code, and "a new rule gets a check, or goes on the unchecked list with its reason".

  • Every rule in CLAUDE.md is either named by a test or on the unchecked list.
  • Removing a rule's id from CLAUDE.md, or a test's id, fails pnpm test.
  • pnpm check passes.

Dashboard boundaries

With the shared parser on app/src, tests that: only api/client.ts calls fetch or builds an EventSource URL from scratch (components use api.logUrl); only platform/ imports @tauri-apps/*; lib/ imports neither vue nor anything under components/; components import the API from api (its index), not from its files. Each gets a rule id in CLAUDE.md's Dashboard layout line. Fix what the tests find.

  • Each rule fails, naming file and line, when broken on purpose.
  • pnpm check passes.

No module-level state in application/

A test fails for a top-level let, or a top-level const holding new Map, new Set, an array or an object literal that the module mutates, in daemon/src/application/. Locks are allowed by name in the test, each with the reason. Tag it with the CLAUDE.md rule's id.

  • Adding a module-level cache to a use case fails pnpm test.
  • pnpm check passes.

Domain language in what people read

A test scans string literals and template text in daemon/src (log lines, CLI output, errors, notifications) and app/src (templates and api/ wording) for phrases CLAUDE.md's Domain language rules out, each listed with the word to use instead: "bring in" (sync), "held" or "on hold" for a repo or the daemon (paused), "plan" or "plans" for the planner's output (proposals). Exceptions are listed by file and phrase, with the reason. Comments and identifiers are not scanned.

  • The test passes on the current code, with any exceptions explained.
  • A log line saying a repo is "held" fails, naming the word to use.
  • pnpm check passes.
