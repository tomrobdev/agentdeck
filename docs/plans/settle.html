A task reaching a final status is one call

When a task reaches done, blocked or failed, its effects (open the PR, notify, warn stuck dependents) are written out by hand after each applyEvent, and two callers forget some: a worker crash (scheduler.ts) fails the task silently, and crash recovery warns dependents but notifies nobody. pr_state, which decides whether a dependency is met, is written with the unguarded updateTask and no history, so refreshPrStates can overwrite a merge recorded while it waits on GitHub. Make settling a task one application call, and make every pr_state write a guarded, recorded event. Written 2026-10-25.

Decisions

Decision Why
A new application/settle.ts exports settle(db, id, event, fields?): Promise<Task | undefined>. It calls db.applyEvent; if the event was refused it returns undefined and does nothing else. Otherwise, by the new status: done opens the PR (openPullRequest) and notifies; blocked and failed notify; then it always calls warnStuckDependents. It returns the task as it is afterwards. One place knows what follows a final status. The deletion test: today the same three effects reappear in worker.ts, sync.ts and scheduler.ts, each with a different subset.
Events a person triggers (mark_done, cancel, retry, approve, reject) keep calling applyEvent directly and keep today's behaviour (no notification). Only settle's callers are the daemon's own paths: the worker's finish, the worker-crash handler, crash recovery, a sync conflict, and pr_merged in the PR refresh. A person who just clicked does not need a notification about it. pr_merged also opens no PR: it already has one.
The notification text moves into the domain as a pure function, e.g. finalNotification(task, repoName, pr): Notification | null in domain/notification.ts, with the wording the worker uses today. Testable without a db, and the same wording for every path.
db/tasks.ts gets recordPr(id, e) with e = { type: 'opened'; url } | { type: 'failed' } | { type: 'closed' } | { type: 'seen'; state }. Each is one guarded UPDATE … WHERE on the current pr_state (and status where it matters), inside atomically with a task_events row of a new type 'pr' (from and to status equal, reason says what happened). Returns whether it applied. A seen event never moves pr_state away from 'merged'. pr_state is lifecycle state (DEPENDENCY_MET reads it), so it gets the same guard and timeline as status. recordMerge already works this way and stays.
updateTask loses pr_url, pr_state, stop_reason, priority and merge_method, keeping only branch and worktree; rename it setCheckout. No caller writes the other fields; a smaller interface is one nobody can misuse.
No schema change: task_events.type is free text, so 'pr' needs only the TaskEventType union and the dashboard's timeline wording. Keeps this a code-only change.

Guarded PR state writes

Add recordPr to db/tasks.ts and the 'pr' event type to domain/task/history.ts. Switch every pr_state write in application/pull-requests.ts (openPullRequest, closePullRequest, refreshPrStates) to it. Shrink updateTask to setCheckout(id, { branch?, worktree }) and update its callers. Give the dashboard's timeline (app/src/components/task/OverviewTab.vue) a line for 'pr' events.

  • grep -rn "pr_state" daemon/src/application shows no direct writes; only recordPr and recordMerge write it.
  • A test: a refresh that read open and then sees GitHub say open again does not undo a recordMerge made in between.
  • A test: opening, failing and closing a PR each add one 'pr' row to the task's history.

One settle call

Add application/settle.ts and the pure notification wording. Route the worker's finish, the scheduler's worker-crash handler, crash recovery's requeued-or-failed tasks (run() in the scheduler), the sync conflict in sync.ts and pr_merged in refreshPrStates through it. Remove the hand-written notify and warnStuckDependents calls those paths have now.

  • A test: a worker that throws leaves its task failed, with a failed notification recorded and its dependents warned.
  • A test: a task failed by crash recovery (restarts exhausted) gets a notification.
  • notifyLater and warnStuckDependents are called from settle.ts and the person-facing use cases only.
  • The existing worker, sync and pull-request tests pass unchanged, apart from imports.

Name resolve runs in the reload log

The scheduler passes tasks: this.running.size to the reload check, which counts resolve runs and the planner as "running tasks". Pass what is actually running (tasks, resolve runs, planner) as an Activity, make Activity.resolves required, and have ReloadInput take an Activity instead of tasks and proposing.

  • A domain test: a reload pending during a resolve run says "1 resolve run", not "1 running task".
